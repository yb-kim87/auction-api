## 0. 결론 요약 (먼저 읽을 것)

사용자가 지정한 원본 데이터셋(**서울시 도시계획사업 현황(서울플랜+) 공간정보**, SHP)과

(`49594772637a6761333370434f574b`, 2026-08-04 발급, `.env`의
`SEOUL_OPENDATA_API_KEY`로 등록 예정)를 사용한다.

추가로 **국토교통부_전국 도시정비사업 통합 데이터**(공공데이터포털 odcloud,
사용자 활용신청 승인 완료, 2026-08-04~)를 확인했다 — 국토부 공공데이터는

## 1. 데이터 수집 우선순위 (요청하신 5단계 구조에 맞춤)

```
PUBLIC_API    : 서울 열린데이터광장 "서울시 도시계획 정비사업 현황"
                (upisRebuild) OpenAPI — 서울시 이용 승인 확보(2026-08-04).
                자동 수집 1순위(구현 우선순위 1위).

PUBLIC_GIS    : 서울시 도시계획사업 현황(서울플랜+) SHP, 의제처리구역 SHP,
                공공데이터포털 "서울특별시 정비사업 데이터"(CSV, 이용제한
                없음) 등 — upisRebuild가 좌표/일부 필드를 못 주는 경우의
                보완 소스. 2순위.

NOTICE_PDF    : 국토이용정보체계/구청 고시문 PDF의 지번 텍스트 파싱
                — 자동화 난이도 높음(레이아웃 비정형), 3순위.

IMAGE_EXTRACTION : 관리자가 이미 만든 이미지 좌표 보정 트레이싱 도구
                (RedevelopmentImageTraceTool, 2026-08-04 구현 완료) — PUBLIC_API로
                커버 안 되는 지역/최신 변경분 보완용, 4순위.

MANUAL        : 관리자 직접 Polygon 작성(이미 구현됨) — 최종 수기 보정 수단, 5순위.
```

파이프라인은 **PUBLIC_API(upisRebuild)로 구역 존재/속성(이름·유형·단계)을
먼저 확보 → 응답에 좌표/경계가 있으면 그대로 쓰고, 없으면 위치명·지역명·
지번을 지오코딩해 경계 폴리곤을 자동 근사 → 근사 결과가 부정확하거나
없는 구역만 IMAGE_EXTRACTION/MANUAL로 보정**하는 흐름이다.

## 2. PUBLIC_API 자동 수집 설계 (서울시 도시계획 정비사업 현황, `upisRebuild`)

### 2.1 API 개요 (실제 호출로 확인 완료, 2026-08-04)
- 엔드포인트: `http://openapi.seoul.go.kr:8088/(인증키)/xml|json/upisRebuild/{시작행}/{끝행}/`
- 인증키: 서울 열린데이터광장 일반인증키(사용자 발급 완료, 2026-08-04 —
  `49594772637a6761333370434f574b`). `.env`에 `SEOUL_OPENDATA_API_KEY`로
  등록(코드에 하드코딩 금지, 기존 `VWORLD_API_KEY` 등과 동일 패턴).
- 페이징: URL의 `{시작행}/{끝행}`으로 페이지네이션(최대 1,000건/호출) —
  전체 **6,584건**이므로 7회 호출로 전량 수집 가능.
- **실제 응답 필드(직접 curl로 앞부분·뒷부분 샘플 확인, 전체 필드)**:

  | 필드 | 설명 | 예시 |
  |---|---|---|
  | `RPT_MNG_CD` | 조서(고시 이력) 관리코드 — 지정/변경/폐지 매 이력마다 별도 발급 | `11170AGZ202003270002` |
  | `PRJC_CD` | 프로젝트(구역) 코드 — 같은 구역의 여러 이력에 걸쳐 값이 이어짐(구역 고유키 후보) | `11170PPL202311150002` |
  | `LOGVM` | 소관 지자체(구청) | `용산구` |
  | `RPT_TYPE` | **이력 유형** — `신설`/`변경`/`폐지` 확인됨(그 외 값 존재 가능) | `폐지` |
  | `LCLSF` | 대분류 — 샘플 전부 `의제처리구역` 고정값으로 보임 | `의제처리구역` |
  | `MCLSF` | 중분류 — 샘플 전부 `정비구역` 고정값으로 보임 | `정비구역` |
  | `SCLSF` | 소분류 — **사업유형에 해당**(주택재개발사업지구/도시환경정비사업지구/도시정비형 재개발구역 등, §4 정규화 매핑 대상) | `도시환경정비사업지구` |
  | `PSTN_NM` | 위치명(텍스트 주소, "일대"/"일원"/"(N필지)" 같은 접미사가 섞여 있어 지오코딩 전 정제 필요) | `한강로2가 2-194호 일대` |
  | `RGN_NM` | **구역명**(사업명) | `신용산역 북측 2구역 도시정비형 재개발구역` |
  | `AREA_EXS` | 변경 전 면적(㎡) | `22324.2` |
  | `AREA_ICDC_CD` | 면적 증감 구분 코드 | `1` |
  | `AREA_CHG` | 증감 면적 | `0.6` |
  | `AREA_CHG_AFTR` | 변경 후 면적(㎡) | `22324.8` |
  | `DCSN_ANCMNT_MNG_CD` | 결정고시 관리코드(고시번호/고시일 연계용) | `11170NTC202311150001` |

- **좌표/폴리곤 필드는 응답에 전혀 없다**(위경도, WKT, X/Y 어떤 형태로도
  없음) — §2.2는 (B) 경로(지오코딩+convex hull)만 유효, (A) 경로는 폐기.
- **"사업단계"(조합설립인가~착공 같은 세부 진행단계)도 이 데이터셋엔
  없다** — `RPT_TYPE`은 진행단계가 아니라 **"구역 지정 고시 이력"**
  (최초 지정=`신설`, 구역 범위 등 변경=`변경`, 구역 해제=`폐지`)이다.
  사용자가 처음 보여준 "한남동 재정비촉진구역 위치도"의 "1구역(해제)"
  표기가 정확히 이 `폐지` 개념과 대응된다. 세부 사업단계까지 필요하면
  §2.4의 보완 소스가 필요.

### 2.2 구역 경계 확보 — 지오코딩 + convex hull (필수 경로로 확정)
1. `PSTN_NM`을 정제한다: 정규식으로 `일대`/`일원`/`\(\d+필지\)`/중복
   공백을 제거해 지번만 남긴다(예: `한강로2가 2-194호 일대` →
   `한강로2가 2-194`). `LOGVM`(구) + 정제된 `PSTN_NM`을 조합해
   `resale-match`의 `city+district+umdNm+jibun` 패턴과 동일하게 주소
   문자열을 만든다(시/도는 항상 "서울특별시" 고정).
2. 기존 `GeocodeService`/`/api/resale-match/geocode` 파이프라인(VWorld
   PARCEL 지오코딩, 2026-08-04 구현·검증됨)으로 좌표 변환.
3. `PSTN_NM` 하나가 여러 지번을 가리키는 경우("890번지 일대", "33번지
   일대(41필지)")가 많아 지오코딩은 대표 지번 1점만 잡힌다 — 여러
   `RPT_MNG_CD`/`PRJC_CD`가 사실상 같은 구역(`RGN_NM` 동일)에 속하면
   그 점들을 모아 **볼록 껍질(convex hull)**을 계산해 근사 폴리곤으로
   삼는다(Graham scan 직접 구현, 외부 라이브러리 불필요).
4. 점이 3개 미만이면 폴리곤 대신 **점 마커 구역**(중심점 + 반경 표시)으로
   저장 — `boundaryType: "POINT_ONLY"`.
5. Convex hull은 실제 경계보다 넓게 잡힐 수 있음(오목한 부분을 못
   표현) — 관리자 화면에 "자동 근사 경계(부정확할 수 있음)" 배지로
   명시하고, 필요시 MANUAL로 재작성하게 한다.
6. 이 데이터셋은 **애초에 정밀 폴리곤을 준 적이 없어서**, "정확한 SHP
   경계"를 원하시면 여전히 §3(SHP, 라이선스 별도 확인 필요)이나
   IMAGE_EXTRACTION/MANUAL 보정이 필요하다 — 이 API는 "구역이 어디
   있는지 대략적 위치 자동 확보"까지가 현실적 목표.

### 2.3 사업단계 보완 소스 — 국토부 전국 도시정비사업 통합 데이터 (실측 확인, 2026-08-04)
`RPT_TYPE`(신설/변경/폐지)만으로는 "사업단계"(조합설립인가/사업시행인가/
관리처분인가/착공 등)를 채울 수 없었는데, 사용자가 별도로 활용신청·승인
받은 **국토교통부_전국 도시정비사업 통합 데이터**(공공데이터포털 odcloud)로
해결 가능함을 Swagger 문서로 확인했다.

- 엔드포인트: `GET https://api.odcloud.kr/api/15160169/v1/uddi:4d7f16a9-b0fd-4d07-b266-d0ad82aeaf34`
  (Base URL `api.odcloud.kr/api`, 파라미터 `page`/`perPage`/`returnType`,
  인증은 헤더 `Authorization` 또는 쿼리 `serviceKey`로 발급받은 일반인증키
  `e41f12b775b61e800cbf372e5a4f0e234171f43344a616c65ee7e87a63feeed6` 사용,
  `.env`에 `MOLIT_UDDI_API_KEY`로 등록).
- 응답 필드: `시도`, `시군구`, `구역명칭`, **`현 사업추진단계`**, `사업유형`,
  `사업시행자`, `공급 예정 세대수`. **전국** 커버(서울 한정 아님).
- **좌표/위경도/폴리곤/지번·주소 필드는 이 데이터에도 없다** — 이 소스는
  "사업단계·시행자·세대수" 속성 보완 전용으로만 쓴다.

**조인 전략**: `upisRebuild`(서울)의 `RGN_NM`(구역명)과 이 데이터의
`구역명칭`을 문자열 매칭으로 연결한다. 두 시스템의 구역명 표기가 완전히
같지 않을 수 있어(공백/버전 차이, 예: `"신림7  주택정비형 재개발사업"` vs
정식 명칭) **정확 일치 실패 시 정규화 후 재시도**(공백 전부 제거 +
"제N구역"/"지구"/"구역" 같은 접미사 제거한 축약형으로 유사도 비교) 하고,
그래도 매칭 안 되면 `stage`를 RPT_TYPE 기준 대분류(구 방식)로
폴백한다. 서울 외 지역은 이 데이터가 유일한 소스이므로, 좌표가 없어
Polygon은 못 만들고 **속성 전용 레코드**(`boundaryType=NONE`, 지도에는
안 뜨고 목록/검색에만 노출)로 우선 저장 — 추후 IMAGE_EXTRACTION/MANUAL로
경계를 보강하면 지도에 올라오게 하는 구조.

### 2.4 세 소스 결합 흐름 요약
```
1. upisRebuild(서울) 전량 수집 → PRJC_CD별로 최신 이력만 남김(§6.2)
   → RGN_NM/SCLSF/PSTN_NM 확보, stage는 RPT_TYPE 대분류로 임시 채움
2. 국토부 통합 데이터 전량 수집 → 시도='서울특별시'인 행을 구역명칭
   기준으로 1의 RGN_NM과 매칭 → 매칭되면 현 사업추진단계로 stage 갱신
3. 서울 외 지역(시도≠서울) 행은 좌표 없이 속성 전용으로 별도 저장
   (boundaryType=NONE)
4. 1에서 확보한 PSTN_NM으로 지오코딩 → convex hull로 폴리곤 근사
   (§2.2) → boundaryType=CONVEX_HULL_APPROX로 승격
```

### 2.5 갱신 주기 및 재수집 트리거
데이터셋 자체 갱신 주기가 "수시(일회성/부정기)"로 명확한 배치 스케줄이
없다 — Seoul 데이터셋은 "반기" 단위였지만 이 CSV 데이터셋은 발행 시점
고정 스냅샷에 가깝다. **주 1회(예: 매주 월요일 새벽) 배치로 전체 재조회**해
차분(diff)만 반영하는 방식을 권장(과도한 API 호출 방지 + 변경 감지).
기존 `DbRetentionService`/`ResaleMatchService`의 `setInterval` 기반
스케줄러 패턴을 그대로 재사용(신규 프레임워크 도입 불필요).

## 3. SHP 파이프라인 설계 (PUBLIC_GIS, 라이선스 승인 후 활성화용으로 미리 준비)

라이선스 문제로 기본 비활성화하지만, 사용자가 서울시에 별도 이용 허락을
받거나 4유형이 아닌 다른 지자체/전국 단위 SHP를 찾을 경우를 대비해 코드
구조는 미리 설계해 둔다.

### 3.1 필요 라이브러리
- **`shapefile`**(npm) — .shp/.dbf를 스트리밍으로 읽어 GeoJSON Feature로
  변환. Node 네이티브 구현이라 GDAL 등 시스템 바이너리 설치 불필요
  (Railway 컨테이너 환경에 유리).
- **`proj4`**(npm) — 좌표계 변환. EPSG:5174(Bessel 1841 TM, 서울시 SHP가
  주로 쓰는 좌표계) → EPSG:4326(WGS84 위경도) 변환에 사용. `proj4` 정의
  문자열은 `epsg.io/5174` 또는 `epsg.io/5186`(GRS80 TM 중부원점, 최근
  국가 SHP는 이쪽으로 이관 중)에서 가져와 하드코딩.
- **`adm-zip`** 또는 **`unzipper`**(npm) — 다운로드한 zip(.shp/.shx/.dbf/.prj
  묶음) 압축 해제.
- `.prj` 파일이 있으면 그 안의 WKT를 파싱해 실제 좌표계를 확인(EPSG 코드
  하드코딩보다 안전) — `proj4`는 WKT를 직접 파싱하는 기능이 약해,
  `.prj` 내용을 `epsg.io`의 매칭 API나 알려진 WKT 패턴 매칭으로 EPSG를
  역추정하는 보조 로직이 필요.

### 3.2 처리 흐름
```
1. zip 다운로드 (관리자 수동 업로드 또는 정기 크론으로 URL 재다운로드)
2. adm-zip으로 압축 해제 → .shp/.shx/.dbf/.prj 존재 확인
   (하나라도 없으면 에러 처리, §6 참고)
3. .prj 읽어 원본 좌표계 확인(EPSG 코드 결정)
4. shapefile 라이브러리로 .shp+.dbf를 GeoJSON Feature 스트림으로 파싱
   (Polygon/MultiPolygon geometry.type 그대로 유지 — shapefile 라이브러리가
   이미 두 타입 다 지원)
5. 각 Feature의 좌표 배열을 순회하며 proj4로 EPSG:4326 재투영
   (MultiPolygon은 폴리곤 배열의 배열이라 중첩 순회 필요)
6. DBF 속성에서 사업유형/사업단계/구역명 필드를 매핑
   (실제 필드명은 데이터셋마다 달라 "필드 매핑 설정표"를 코드가 아닌
   DB/설정 파일로 분리 — 새 데이터셋 추가 시 코드 수정 없이 매핑 추가)
7. §5 DB 스키마에 upsert(§7 중복판별 키 기준)
```

## 4. 사업유형 분류 (재개발·재건축·신속통합기획·모아타운 등)

원본 데이터의 `지구유형`/`정비유형` 필드 값이 지자체마다 표기가 다를 수
있어(예: "재개발", "재개발사업", "재개발정비구역" 등 변형), **정규화 매핑
테이블**을 둔다:

```ts
type RedevelopmentProjectType =
  | "REDEVELOPMENT"      // 재개발
  | "RECONSTRUCTION"     // 재건축
  | "FAST_TRACK"         // 신속통합기획(오세훈표 신통기획)
  | "MOATOWN"            // 모아타운
  | "URBAN_RENEWAL_ETC"  // 그 외 도시정비형/자율주택정비 등
  | "UNKNOWN";
```

원본 텍스트 → 정규화 코드 매핑은 코드에 하드코딩하지 않고 DB 테이블
(`redevelopment_type_mapping`: `rawText`, `normalizedType`)로 관리 —
새 표기가 나올 때마다 관리자가 화면에서 추가할 수 있게(마이그레이션 없이).

## 5. DB 스키마 설계

기존 `RedevelopmentZone`(2026-08-04 오늘 구현)을 확장한다. 기존 필드
(`name`, `region`, `stage`, `memo`, `polygon`, `color`)는 유지하고 아래
필드를 추가:

```ts
@Entity("redevelopment_zones")
export class RedevelopmentZone {
  // ...기존 필드 유지...

  /** 사업유형(재개발/재건축/신속통합기획/모아타운 등, §4 정규화 코드) */
  @Column({ type: "text", nullable: true })
  projectType!: string | null;

  /** 데이터 출처 — 어느 파이프라인이 이 구역을 만들었는지(§1 5단계) */
  @Column({ type: "text", default: "MANUAL" })
  source!: "PUBLIC_GIS" | "PUBLIC_API" | "NOTICE_PDF" | "IMAGE_EXTRACTION" | "MANUAL";

  /** 원본 데이터셋 식별자(예: "seoul-jeongbi-csv-2026H1") — §7 중복판별에 사용 */
  @Column({ type: "text", nullable: true })
  sourceDatasetId!: string | null;

  /** 원본 데이터의 고유 식별 키(예: 고시번호, 구역명+법정동 조합) —
   * §7 중복판별 키의 실제 값 */
  @Column({ type: "text", nullable: true })
  sourceKey!: string | null;

  /** 원본 데이터 기준일자(고시일 등) — "기준일자" 요구사항 */
  @Column({ type: "date", nullable: true })
  asOfDate!: string | null;

  /** 폴리곤이 실제 경계인지, convex hull 근사인지, 점 마커 대체인지 */
  @Column({ type: "text", default: "MANUAL" })
  boundaryType!: "EXACT" | "CONVEX_HULL_APPROX" | "POINT_ONLY" | "NONE" | "MANUAL";
  // NONE: 국토부 통합 데이터처럼 좌표 자체가 없어 지도에는 안 뜨고
  // 목록/검색 전용으로만 존재하는 속성 레코드(§2.4)

  /** 자동 수집 파이프라인이 마지막으로 이 구역을 갱신한 시각 —
   * 사람이 MANUAL로 마지막 수정했으면 자동 갱신이 덮어쓰지 않게 판단 */
  @Column({ type: "timestamp", nullable: true })
  lastAutoSyncedAt!: Date | null;
}
```

인덱스: `(source, sourceDatasetId, sourceKey)` 유니크 인덱스 — §7 중복판별의
근거.

## 6. 갱신 주기 및 중복 판별 키(§10 요구사항)

### 6.1 중복 판별 키
`sourceKey`를 다음 규칙으로 생성한다(출처별로 다름, 자연키가 있으면 그걸,
없으면 조합키):

- **PUBLIC_API(정비사업 데이터)**: 원본에 `고시번호`가 있으면 그것을
  그대로 사용(가장 안정적인 자연키). 없으면 `정비구역명 + 법정동명`
  조합을 정규화(공백 제거, 소문자화 없음—한글이라 트림만)해서 사용.
- **PUBLIC_GIS(SHP)**: DBF의 관리코드(예: "결정고시관리코드")가 있으면
  그것. 없으면 구역명+지오메트리 중심점 좌표를 반올림해 조합.
- **MANUAL/IMAGE_EXTRACTION**: 사람이 직접 만든 건 애초에 자동 갱신
  대상이 아니므로 `sourceKey`는 null로 두고 자동 파이프라인이 절대
  건드리지 않는다(§6.2).

### 6.2 갱신(신규 생성 금지) 로직
```
매 수집 사이클마다:
1. 새로 받아온 레코드의 sourceKey로 기존 RedevelopmentZone을 조회
   (WHERE source=X AND sourceDatasetId=Y AND sourceKey=Z)
2. 있으면 UPDATE(폴리곤/속성 갱신) + lastAutoSyncedAt 갱신
   — 단, 관리자가 그 구역을 MANUAL로 마지막 수정한 이력이 있으면
   (updatedAt > lastAutoSyncedAt 이면서 boundaryType이 MANUAL로 바뀌어
   있는 경우) 자동 갱신이 덮어쓰지 않고 "충돌 감지" 로그만 남기고 skip
   — 관리자가 수기로 고친 폴리곤을 자동 배치가 되돌리는 사고 방지.
3. 없으면 INSERT(신규 구역)
4. 이번 수집에서 안 보인 기존 자동수집 구역(source=PUBLIC_API 등)은
   삭제하지 않고 "폐지 후보"로만 표시(예: 별도 status 필드 또는 memo에
   자동 기록) — 데이터 소스 쪽의 일시적 누락일 수 있어 즉시 삭제는 위험.
   관리자가 확인 후 수동 삭제.
```

## 7. 오류 처리

| 실패 지점 | 처리 방침 |
|---|---|
| zip 다운로드 실패(네트워크/URL 변경) | 재시도 3회(지수 백오프) 후 실패 시 관리자에게 알림(기존 `TelegramAlertService` 재사용), 마지막 성공 데이터 유지 |
| zip 안에 shp/shx/dbf/prj 중 하나라도 없음 | 그 파일셋 전체를 건너뛰고 사유를 로그(`crawler_log`류 패턴 재사용)에 남김 — 부분 파일로 억지 파싱 시도 안 함(좌표 깨짐 위험) |
| `.prj` 좌표계를 알려진 EPSG로 매칭 실패 | 안전을 위해 그 배치 전체를 반려(추측 좌표계로 잘못 변환해 지도에 엉뚱한 위치로 찍히는 사고가 VWorld 지오코딩에서 실측된 적 있음 — ROAD/PARCEL 오매칭 사고, 2026-07-23 이력 참고) — 수동 확인 요청 |
| 지오코딩 실패(주소 매칭 안 됨, 일부 번지) | 실패한 번지만 제외하고 나머지 점으로 convex hull 계산, 실패율이 전체의 50% 넘으면 그 구역은 POINT_ONLY로 강등하지 않고 생성 자체를 보류(부정확한 경계가 만들어지는 것보다 안전) |
| convex hull 계산 결과 자기교차(degenerate) | 점이 일직선이거나 2개뿐이면 POINT_ONLY로 강등 |
| DB upsert 중 unique 제약 충돌(동시 실행) | 배치는 단일 인스턴스에서만 실행되도록 실행 중 플래그(기존 `ResaleMatchService.runOnce()`의 "이미 실행 중이면 무시" 패턴 재사용) |
| 사업유형 매핑 테이블에 없는 신규 원문 값 | `UNKNOWN`으로 저장 + 관리자 화면에 "미분류 N건" 배지로 노출, 매핑 테이블에 추가하면 다음 배치부터 자동 재분류 |

## 8. 프론트엔드 반영 (기존 카카오맵 재사용)

이미 구현된 `RedevelopmentMapView.tsx`/`RedevelopmentTab.tsx`을 그대로
재사용하되:
- 자동 수집 구역은 `source`별 아이콘/뱃지 구분(예: "공공데이터 자동수집"
  vs "관리자 직접 작성").
- `boundaryType=CONVEX_HULL_APPROX`인 구역은 폴리곤 테두리를 점선으로
  표시해 "근사 경계"임을 시각적으로 구분.
- MultiPolygon 지원: 카카오맵 `Polygon` 컴포넌트는 단일 path만 받으므로,
  MultiPolygon은 하위 폴리곤마다 별도 `kakao.maps.Polygon` 인스턴스를
  만들어 같은 `zoneId`로 묶어 관리(클릭 시 어느 조각을 눌러도 같은 구역
  정보/포함 물건 목록이 뜨도록).
- 물건 포함 판별(`isPointInPolygon`)도 MultiPolygon이면 하위 폴리곤 중
  하나라도 포함하면 true로 판정(OR 조건).

## 9. 단계별 구현 순서 제안(구현 시작 시 참고용, 지금은 미구현)

1. `RedevelopmentZone` 엔티티 확장 마이그레이션(§5) — 기존 테이블에 컬럼
   추가만이라 무중단.
2. `projectType` 정규화 매핑 테이블 + 관리자 화면 CRUD.
3. PUBLIC_API 수집기(정비사업 데이터 OpenAPI 클라이언트 + convex hull
   재구성 + upsert 로직) — 라이선스 안전, 최우선 구현.
4. §6.2 갱신/충돌감지 로직 + 스케줄러(주 1회).
5. 프론트 배지/점선 표시(§8).
6. SHP 파이프라인(§3)은 라이선스 승인 시점에 맞춰 마지막에 구현.
