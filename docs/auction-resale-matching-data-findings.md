# 매도 추정 기능 — 실측 데이터 조사 결과 (원본 API 필드 전수 확인)

날짜: 2026-07-28
관련 설계 문서: [auction-resale-matching-design.md](./auction-resale-matching-design.md)
샘플 원본 파일: `crawler/samples/*.json` (실제 응답 원본, 재분석용으로 보존)

이 문서는 [설계 문서](./auction-resale-matching-design.md)를 실제 데이터로
검증하기 위해 아파트 물건 1건을 표본으로 **v3(httpx) 경로**로 직접
크롤링하고, 탱크옥션/네이버부동산 원본 API 응답을 필드 단위로 전수
조사한 결과다. 설계 문서의 "5장 현재 데이터로 가능한 부분"이 이 조사로
상당 부분 갱신됐다 — **이전에 "미보유/2단계 확장"으로 분류했던 항목
다수가 실제로는 이미 원본 API에 존재하고, 우리 파서가 버리고
있었을 뿐**임이 확인됐다.

## 2. 탱크옥션(`AuctView.php`) — 매각대금완납일 확보 가능 확인

### 2.1 결론
**매각대금완납일은 `histInfo.items[]`의 상태코드(`sta`) 시퀀스에서 확보
가능하다.** 별도 API 연동 없이 이미 매 크롤링마다 받고 있는 응답
안에 있다.

### 2.2 상태코드(`sta`) 매핑 — 실측으로 신규 확인분 포함

기존 `crawler/tank_detail.py`의 `_BID_HIST_STATE_LABELS`에는 아래
굵게 표시한 4개(1215/1216/1218/1219)가 **없었다.** 이번 조사로
탱크옥션 페이지 렌더 텍스트("기일내역" 섹션, "진행내역" 요약 문구)와
`histInfo` 날짜를 대조해 확정했다.

| sta 코드 | 라벨 | 기존 코드 매핑 여부 | 확인 방법 |
|---|---|---|---|
| 1110 | 진행 | ✅ 기존 | - |
| 1111 | 유찰 | ✅ 기존 | - |
| 1210 | 매각 | ✅ 기존 | - |
| 1211 | 매각허가결정 | ✅ 기존 | 페이지 렌더: "매각결정기일 : 2026-03-11 - 매각허가결정" |
| 1230 | 대금지급기한(설정/고지) | ✅ 기존(라벨은 있었으나 정확한 의미 미확인 상태였음) | `histInfo`상 1211과 같은 날(03-11)에 발생 — 지급기한을 설정/고지하는 행정 이벤트로 추정 |
| **1215** | **지급기한(공고된 마감일 자체)** | ❌ 신규 확인 | 페이지 렌더: "지급기한 : 2026-04-17" ↔ `histInfo` sta=1215 날짜(04-17) 일치 |
| **1216** | **대금완납(납부일)** | ❌ 신규 확인, **이번 조사의 핵심 발견** | 페이지 상단 요약: "매각 7일 매각결정기일 **30일** 납부 40일 배당종결" → 매각허가결정(03-11)+30일=04-10, `histInfo` sta=1216 날짜(04-10)와 정확히 일치 |
| **1218** | **배당기일(진행)** | ❌ 신규 확인 | 페이지 렌더: "배당기일 : 2026-05-20" ↔ `histInfo` sta=1218 날짜 일치 |
| **1219** | **배당종결** | ❌ 신규 확인 | 페이지 렌더: "배당종결 : 2026-05-20" ↔ `histInfo` sta=1219 날짜 일치, `baseInfo.stateNm`(사건 최종상태)도 "배당종결"로 일치 |

### 2.3 중요 발견 — "지급기한"(공고일)과 "실제 완납일"은 다른 날짜

이번 표본에서 매수인은 공고된 지급기한(**04-17**)보다 **7일 이른
04-10에 실제 완납**했다. 즉:

```
매각(1210, 03-04)
  → 매각허가결정(1211, 03-11)
  → 지급기한 고지(1230, 03-11, 같은날)
  → 【실제 대금완납(1216, 04-10)】 ← 이게 진짜 소유권 취득일(anchor)
  → 지급기한 공고일 자체를 나타내는 행(1215, 04-17) — 이미 완납된 후 뒤늦게 기록되는 행정 로그로 보임
  → 배당기일(1218, 05-20)
  → 배당종결(1219, 05-20)
```

**결론**: 설계 문서에서 제안한 "완납일 컬럼"은 `1216` 상태코드의
`bid_dt` 값을 그대로 쓰면 된다. **완납일 확보를 위한 별도 대법원
스크래핑이나 외부 API가 필요 없다** — 이는 설계 문서 로드맵 "0단계
전제조건"이 이미 충족됐다는 뜻이다.

**주의(추가 검증 필요)**: 이 매핑은 표본 1건으로 확정한 것이다. 다른
법원/사건 유형(강제경매 vs 임의경매, 재경매, 배당 없이 종결되는
사건 등)에서 시퀀스 순서나 sta 코드가 다르게 나타날 수 있으므로,
실제 구현 전 **표본을 10~20건으로 늘려 재검증**을 권장한다(설계
문서 로드맵 0단계에 반영 필요).

### 2.4 참고 원본 파일
`crawler/samples/tank_auctview_sample.json` — `histInfo`, `baseInfo`,
`dstbInfo`(배당 상세) 전체 포함.

## 3. 네이버부동산 실거래 API(`/front-api/v1/complex/pyeong/realPrice`)

### 3.1 우리가 현재 쓰는 필드 (기존 `naver_httpx.py: _fetch_real_price`)
`tradeDate`(계약일), `floor`(층), `dealPrice`(거래가), `tradeYear` 만
텍스트 블록으로 가공해 저장하고 있었다.

### 3.2 원본 응답의 전체 필드 (실측, 표본 1행)
```json
{
  "tradeDate": "2026-04-21",
  "tradeYear": "2026",
  "floor": 20,
  "dealPrice": 248000000,
  "deposit": 0,
  "monthlyRent": 0,
  "isDelete": false,
  "tradeCategory": "중개거래",
  "registrationDate": "2026-06-29",
  "propertyType": "NORMAL",
  "isRenew": false
}
```

### 3.3 지금까지 버리고 있던, 매칭 정확도에 바로 쓸 수 있는 필드

| 필드 | 의미 | 활용 가치 |
|---|---|---|
| **`registrationDate`** | 등기접수일(소유권이전등기) | 설계 문서에서 "추가하면 좋은 데이터"로 분류했던 **"등기 변경"이 이미 이 응답에 들어있다.** 계약일(신고 기준)보다 법적으로 더 확정적인 소유권 이전 시점 — TimeScore 계산의 상한 검증(등기일이 완납일보다 너무 이르면 이상 거래로 의심 가능)이나, 완납일↔등기일 gap을 별도 신호로 추가할 수 있음 |
| **`tradeCategory`** | "중개거래" / (다른 값으로 "직거래" 존재 가능성, 이번 표본은 전부 중개거래만 관측) | **직거래(당사자 간 직접 거래)는 다운계약·특수관계 거래 위험이 상대적으로 높다** — PriceScore 신뢰도에 반영할 수 있는 리스크 신호. 설계 문서에 없던 새 서브요소 |
| **`propertyType`** | "NORMAL"(그 외 값 미관측, 분양권/입주권 등을 구분할 가능성) | 일반 매매가 아닌 특수 거래 유형을 걸러내는 필터 후보 |
| `isDelete` | 거래 취소(해제) 여부 | 이미 필터링에 쓰고 있음(`if row.get("isDelete"): continue`) — 정상 |

**결론**: 코드 한 줄도 안 바꿔도 되는 게 아니라, **기존에 이미 호출하고
있는 API 응답에서 파싱 단계만 넓히면** 되는 항목들이다. 신규 API
연동이 필요 없다 — 설계 문서 5장의 "국토부 API 연동 필요" 항목 중
일부(신고 정확도 보강)는 이 필드만으로도 상당 부분 대체 가능해
보인다(단, 여전히 **동(棟) 정보는 이 API에 없다** — 이 결론은
설계 문서와 동일하게 유지).

### 3.4 참고 원본 파일
`crawler/samples/naver_realprice_sample.json`

## 4. 네이버부동산 매물(호가) API(`/front-api/v1/complex/article/list`)

### 4.1 우리가 현재 쓰는 필드
가격·동·층 정도만 텍스트로 가공(`priceDetail`). article 고유ID나
노출일자 등은 전혀 저장하지 않는다.

### 4.2 원본 응답에서 새로 확인된, 설계에 즉시 반영 가능한 필드

표본 매물(articleNumber=2637371889) 기준 핵심 필드만 정리(전체는
`crawler/samples/naver_articles_sample.json` 참고):

```json
{
  "articleNumber": "2637371889",
  "dongName": "105",
  "spaceInfo": {
    "supplySpace": 95.31,
    "exclusiveSpace": 65.69,
    "supplySpaceName": "95A",
    "exclusiveSpaceName": "65.69A",
    "nameType": "A"
  },
  "buildingInfo": {
    "buildingConjunctionDate": "20190529",
    "approvalElapsedYear": 8
  },
  "verificationInfo": {
    "verificationType": "OWNER",
    "isAssociationArticle": false,
    "exposureStartDate": "2026-07-11",
    "articleConfirmDate": "2026-07-11"
  },
  "brokerInfo": { "cpId": "bizmk", "brokerageName": "...", "brokerName": "..." },
  "articleDetail": {
    "direction": "WS",
    "directionStandard": "거실 기준",
    "articleFeatureDescription": "인기있는 타입, ...",
    "directTrade": false,
    "floorInfo": "고/40",
    "floorDetailInfo": {
      "targetFloor": "고", "totalFloor": "40",
      "floorType": "20", "residenceType": "1"
    }
  },
  "priceInfo": {
    "dealPrice": 245000000,
    "managementFeeAmount": 200000,
    "priceChangeStatus": 1,
    "priceChangeHistories": [
      { "modifiedDate": "2026-07-11T10:08:29", "dealPrice": 235000000 },
      { "modifiedDate": "2026-07-22T15:25:55", "dealPrice": 245000000 }
    ]
  }
}
```

| 필드 | 의미 | 설계 문서와의 관계 |
|---|---|---|
| **`articleNumber`** | 매물 고유 ID | 설계 문서 `naver_listing_snapshot.articleId`로 그대로 사용 가능 — 별도 ID 채번 로직 불필요 |
| **`exposureStartDate`** | **매물이 처음 노출(등록)된 날짜** | 설계 문서가 요구한 **"네이버 매물 최초 등록일"이 API가 이미 직접 제공하는 필드다.** 스냅샷을 매일 비교해서 "첫 관측일"을 추론(근사)할 필요가 없다 — 크롤링 1회만으로도 정확한 최초등록일 확보 |
| `articleConfirmDate` | 매물 최근 확인(갱신)일 | 크롤링 시점마다 이 값이 갱신되면 "아직 살아있는 매물"이라는 뜻 — 삭제 감지(사라짐)는 여전히 일별 스냅샷 diff가 필요하지만, "얼마나 최근에 확인됐는지"는 이 필드로 보조 검증 가능 |
| `dongName` | 동 | 이미 알고 있던 정보(호가에는 동이 있음) — 재확인 |
| **`spaceInfo.nameType`**, `exclusiveSpaceName`(예: "65.69A") | **A/B 타입 라벨** | 설계 문서 3.2절에서 "라벨까지 저장하도록 확장하면 오탐이 거의 사라진다"고 제안했던 바로 그 데이터. 이미 원본에 명시적으로 존재(`nameType: "A"`) — 매물뿐 아니라 이 라벨을 실거래에도 연결할 근거가 됨(같은 단지의 같은 면적이 매물에서 A/B로 갈리면, 실거래도 해당 면적 그룹의 라벨을 상속해 유추 가능) |
| `direction`(방향, 코드값 "WS" 등), `directionStandard` | 향 | 설계 문서에서 "약한 보조 신호"로 분류했던 향(방향) 정보 확인됨 — 코드값이라 별도 디코딩 테이블 필요 |
| `verificationType`("OWNER") | 매물 검증 유형(집주인 확인 매물 등) | 매물 신뢰도 신호 — 설계 문서에 없던 항목, 허위매물 필터링에 참고 가능 |
| **`priceInfo.priceChangeHistories`** | **가격 변동 이력** | 설계 문서에 없던 발견. 최초등록가 대비 최종 호가 변동 추이를 알 수 있어, "매물이 삭제되기 직전 가격"과 "실거래가"를 비교하는 정밀 매칭에 활용 가능(단순 최초가만 비교하는 것보다 정확) |
| `directTrade` | 집주인 직거래 매물 여부 | 3.3절의 `tradeCategory`(중개/직거래)와 대응되는 매물 측 신호 |
| `managementFeeAmount` | 매물에 표시된 월 관리비 예상액 | 이번 기능과 직접 관련은 적으나, 기존 `unpaidFeeAmount`(체납관리비)와는 별개 개념이니 혼동 주의 |
| `floorInfo`("고/40") | 층 구간 표기 | **주의**: 매물 측 층 표기가 항상 정확한 숫자가 아니라 "저/중/고" 구간으로만 노출되는 경우가 있음(이 표본이 그 예). 층 정밀 매칭은 실거래(`realPrice`) 쪽의 정확한 숫자 층을 우선 신뢰하고, 매물 층은 보조 신호로만 사용해야 함(설계 문서 4장 FloorScore 계산 시 유의) |
| `buildingConjunctionDate` | 건물 사용승인일 | 이미 `auctions.builtYear`로 확보 중인 정보와 대조 가능(단지 신뢰성 검증용) |

## 5. 설계 문서(5장) 갱신 요약

| 항목 | 기존 설계 문서 분류 | 이번 조사 후 갱신 |
|---|---|---|
| 매각대금완납일 | "0단계 전제조건, 별도 조사 필요" | ✅ **확보 가능 확인**(`histInfo` sta=1216) — 0단계 완료 |
| 네이버 매물 최초 등록일 | "2단계, 매일 스냅샷 diff로 근사 추정 필요" | ✅ **API가 `exposureStartDate`로 직접 제공** — 근사 추정 불필요, 스냅샷은 "삭제 시점" 감지용으로만 필요 |
| 등기 변경(소유권이전등기일) | "★★★, 별도 국토부/등기 API 연동 필요" | ✅ **네이버 실거래 API의 `registrationDate`로 이미 확보 가능** — 신규 연동 불필요 |
| A/B 타입 라벨 | "★★★★, 확장 필요" | ✅ **매물 API의 `spaceInfo.nameType`/`exclusiveSpaceName`으로 이미 확보 가능** |
| 방향(향) | "★★, 보조 신호" | ✅ 매물 API에 `direction` 코드값으로 존재(디코딩 테이블만 있으면 즉시 사용) |
| (신규) 거래유형(중개/직거래) | 설계 문서에 없었음 | 🆕 실거래·매물 양쪽에 존재, 리스크 신호로 스코어링에 추가 검토 |
| (신규) 가격 변동 이력 | 설계 문서에 없었음 | 🆕 매물 API `priceChangeHistories` — 매물 삭제 직전 최종가 정밀 비교에 활용 가능 |
| (신규) 매물 검증유형 | 설계 문서에 없었음 | 🆕 허위매물 필터링 보조 신호 |
| 층 정보 신뢰도 | 구분 없었음 | ⚠️ **매물 측 층은 "저/중/고" 구간으로만 나올 수 있음** — 실거래 측 숫자 층을 우선하도록 명확화 필요 |

### 5.1 국토부(MOLIT) 실거래가 API에 대한 판단

사용자가 언급한 "국토부실거래" 탭이 탱크옥션 페이지에 실제로 존재함을
확인했으나(캡처 텍스트 메뉴 목록에서 확인), 이 탭이 호출하는 정확한
API 엔드포인트는 이번 조사에서 특정하지 못했다(별도 조사 필요, 낮은
우선순위 — 네이버 실거래 API만으로 이미 충분한 필드를 확보했기 때문).

공공데이터포털의 **국토교통부 아파트매매 실거래가 상세자료 Open
API**는 별도 신청(API 키 발급)이 필요한 공식 경로이며, 일부 연도/
단지에 한해 동(`aptDong`) 필드를 공개하기도 한다(설계 문서 5.2절
기존 서술 유지). 네이버 실거래 API로 커버 안 되는 유일한 공백(동
정보)을 메울 수 있는 유일한 공식 경로이므로, **정확도를 한 단계
더 끌어올리고 싶을 때(설계 문서 로드맵 4단계 이후) 검토 대상**으로
유지한다 — 이번 조사로 우선순위가 낮아진 것은 아니고, 단지 "당장
없어도 서비스 가능한 수준"이 확인됐다는 의미다.

## 7. 追記 (2026-07-28) — 국토부 실거래가(동 정보 포함) 직접 확보 가능 확인

사용자 요청: "2025타경811 이거 우리 DB에 있는 물건이긴한데 탱크옥션
크롤링하면 국토부 실거래가에 동정보가 있긴하거든?? 확인해 볼래?
그리고 국토부 실거래가 정보를 우리가 직접 가져올 수 잇는지도
확인해줘"

### 7.1 결론

**둘 다 확인됨.** 탱크옥션 페이지에 "국토부실거래" 탭이 실제로 존재하고,
호출하는 API가 **`POST /molit/res/TradePriceApi.php?mode=trade-price`**
임을 확인했다. 이 API는 **국토교통부 공식 실거래가 원본 데이터**를
반환하며(탱크옥션이 자체 조사한 게 아니라 정부 신고 데이터를 그대로
프록시), **동(棟) 필드를 포함한다.**

### 7.2 표본 검증 (tid=`2500112`, 2025타경811, 인천 계양구 계산동
계산더샵아파트)

이 API를 v3(httpx)로 **직접 호출**해 재현에 성공했다. 요청 파라미터는
전부 우리가 이미 갖고 있는 데이터(`AuctView.php`의 `baseInfo` — x/y좌표·
pnu·도로명주소·건물명 등, `EnvViewData.php`의 `dtDj.ka_code` — 단지
코드)로 조립 가능하며, **탱크옥션 API 키나 별도 인증 없이 우리 기존
로그인 세션만으로 호출된다.**

응답 예시(`item[]`, 최근 거래):
```json
{
  "구분": "매매", "계약년월일": "2026.04.14",
  "전용면적": 101.8427, "동": "102", "층": "3",
  "거래금액": 42000, "건축년도": "2007"
}
```

### 7.3 동(棟) 공개 비율 — 정밀 통계(표본 1개 단지, 335건 전수)

| 구간 | 거래 건수 | 동 정보 있음 | 비율 |
|---|---|---|---|
| 2024년 이전 계약 | 309건 | 0건 | **0%** |
| 2024년 이후 계약 | 26건 | 13건 | **50%** |

**정정**: 설계 문서(5.1절)에서 "일부 최신 연도 단지는 동 필드가
채워진다"고 서술했던 부분을 더 정밀하게 갱신한다 — **2024년 이전
데이터는 이 표본에서 동이 전혀 공개되지 않았고(0%), 2024년 이후에도
절반만 공개된다(50%, 매매 유형에서만 관측되고 전세·월세는 이 표본
전부 미공개).** 즉 "있으면 좋고 없어도 정상"이라는 설계 원칙(동을
가점 요소로만 쓰고 필수 조건으로 쓰지 않음)은 여전히 유효하며, 오히려
이번 정밀 수치로 더 근거가 확실해졌다.

### 7.4 "우리가 직접 가져올 수 있는가" — 두 가지 경로, 둘 다 가능

**경로 A. 탱크옥션 프록시 재사용 (즉시 가능, 추가 설정 0)**
- 이미 로그인 중인 크롤러 세션으로 `POST /molit/res/TradePriceApi.php`를
  그대로 호출하면 된다. 신규 API 키 발급/등록 불필요.
- 단점: 탱크옥션이 내부적으로 이 엔드포인트를 바꾸면 우리 쪽도 깨짐
  (외부 서비스의 비공식 내부 API에 의존하는 리스크).

**경로 B. 공공데이터포털 공식 API 직접 연동**
- 부가세계산기용으로 이미 `BUILDING_REGISTER_API_KEY`(data.go.kr
  인코딩 키, `BldRgstHubService`용)가 등록돼 있음을 확인했다
  (`auction/.env.local`).
- 국토교통부 "아파트매매 실거래 상세 자료" API도 같은 data.go.kr
  국토교통부(제공기관코드 1613000) 계정 체계 안에 있는 별개
  상품이라, **같은 계정에서 이 API를 추가로 활용신청(대부분 즉시
  자동승인)하면 동일 키 체계로 공식 경로 확보 가능**하다.
- 장점: 탱크옥션 비공식 API 의존 없이 독립적으로 동작, 공식 SLA.
- 단점: 신규 활용신청 절차 필요(사용자 계정 조치 필요, 개발 작업
  아님).

**권장**: 1단계 구현은 **경로 A**(탱크옥션 프록시)로 시작 — 이미
매 크롤링마다 확보하는 데이터만으로 즉시 호출 가능하고 별도 설정이
없다. 안정성이 우려되면 이후 **경로 B**로 전환/이중화하는 걸 고려한다.

### 7.5 설계 문서 갱신 필요 사항

- DB 스키마의 `actual_trade` 테이블에 이 API 고유 필드(`구분`=거래유형
  매매/전세/월세, `건축년도`)를 반영 검토.
- 실거래 데이터 소스 우선순위를 "네이버 스크래핑" 단일에서
  "국토부(탱크 프록시) + 네이버" 이중 소스로 조정 검토 — 국토부
  데이터가 더 공식적이고(정부 신고 기준) 동 정보까지 일부 포함하므로
  주 소스로, 네이버는 등록일(`exposureStartDate`)·매물이력 등 국토부에
  없는 보완 정보용으로 역할 분담 가능.

### 8.2 교차 검증 — 탱크옥션 프록시와 완전히 일치

동일 물건(2025타경811, tid=2500112, 인천 계양구 서운동 178
서운동경남아너스빌 103동 9층902호)의 단지 실거래를 공식 API로 조회한
결과, 탱크옥션 프록시(`/molit/res/TradePriceApi.php`)에서 봤던 것과

두 소스(탱크 프록시 vs 공식 API)가 동/층/면적/가격/계약일 전부
일치 — **데이터 신뢰성 상호 검증 완료.**

### 8.3 공식 API가 탱크 프록시보다 추가로 주는 필드

| 필드 | 의미 | 매칭 알고리즘 활용 가치 |
|---|---|---|
| **`rgstDate`** | 등기접수일 | 네이버 API의 `registrationDate`와 동일 개념을 **국토부 공식 데이터로 직접 확보** — 별도 스크래핑 없이 가장 신뢰도 높은 소유권이전 시점 확보 |
| **`buyerGbn`/`slerGbn`** | 매수자/매도자 구분(개인/법인) | 신규 발견. 법인 간 거래·특수관계 거래(예: 계열사 매도) 필터링에 활용 가능 — 개인↔개인 거래가 통상적인 매도 흐름과 가장 부합 |
| `dealingGbn` | 중개거래/직거래 | 네이버 API의 `tradeCategory`와 동일 개념, 공식 소스로 재확인 |
| `cdealDay`/`cdealType` | **계약 해제일/해제사유** | **중요**: 이 필드가 채워진 거래는 계약이 해제(취소)된 것이므로 **매칭 후보에서 반드시 제외해야 함** — 설계 문서 2장 하드필터에 추가 필요 |
| `landLeaseholdGbn` | 토지임대부 여부(Y/N) | 일반 소유권 매매가 아닌 특수 케이스 필터링 |
| `estateAgentSggNm` | 중개업소 소재 시군구 | 보조 정보 |
| `aptDong` | 동 | 이번 조사에서 재확인 — 이 구(인천 계양구) 전체 100건 표본 기준 **75%가 동 정보 포함**(앞서 단일 단지 표본 50%보다 높음, 지역/단지별 편차 있음을 시사) |

### 8.4 결론 — 실거래 데이터 소스 우선순위 갱신

국토부 공식 API가 **탱크옥션 프록시(비공식 의존)와 네이버
스크래핑(동 정보 전무)의 단점을 모두 보완**하는 최상위 소스임이
확인됐다:

1. **국토부 공식 API**(신규, `RTMSDataSvcAptTrade`) — 동·등기일·매수매도자구분·
   계약해제여부까지 포함한 가장 신뢰도 높은 소스. `actual_trade` 테이블의
   **주 소스로 채택 권장.**
2. 네이버 실거래 API — `exposureStartDate`(매물 최초등록일) 등 국토부에
   없는 매물 이력 연결용 보조 소스로 역할 재조정.
3. 탱크옥션 프록시 — 이제 필수는 아님(공식 API로 대체 가능), 다만
   탱크옥션이 이미 PNU/좌표 등을 함께 제공해 편의성은 있어 백업/교차검증
   용도로 유지 검토.

## 9. 追記 (2026-07-28) — 탱크옥션 프록시 vs 공식 API 정밀 대조

동일 단지(서운동경남아너스빌, tid=2500112) 2024~2026년 매매 거래
14건 전부를 두 소스에서 각각 가져와 1:1 대조했다.

### 9.1 결과: 14건 중 13건 완전 일치, 1건에서 동 정보 차이 발견

계약일·층·전용면적·거래금액은 **14건 전부 완전히 일치**했다(오탐/누락
없음). 다만 **동(棟) 필드에서 1건 차이가 확인됐다**:

| 계약일 | 층 | 면적 | 금액 | 탱크옥션 프록시(`동`) | 공식 API(`aptDong`) |
|---|---|---|---|---|---|
| 2025.06.03 | 3층 | 101.8427㎡ | 43,500만원 | **빈 값("-")** | **"101"** |

즉 **완전히 동일한 실거래 1건에 대해, 탱크옥션 프록시는 동 정보를
빈 값으로 보여주는데 공식 API는 "101동"까지 정확히 제공한다.**

### 9.2 결론

**공식 API가 탱크옥션 프록시보다 최소한 같거나 더 많은 동 정보를
제공한다** — 이번 표본에서 탱크 쪽이 공식 API보다 더 많은 정보를
가진 사례는 없었고, 반대로 공식 API가 탱크에 없던 동 정보를 추가로
보여준 사례가 1건 확인됐다. 추정 원인: 탱크옥션의 "차트/통계용"
캐시(`chartItem`)가 최신 원본과 완전히 동기화되지 않았거나, 자체
단순화 로직으로 일부 오래된 캐시 항목의 동 필드를 누락시켰을
가능성(확정적이지 않음, 추가 표본 필요).

여기에 8.3절에서 정리한 추가 필드(`rgstDate`, `buyerGbn`/`slerGbn`,
`cdealType`, `landLeaseholdGbn`)까지 더하면, **공식 API가 정보량·
정확도 양쪽에서 탱크옥션 프록시를 상회한다**는 결론이 이번 정밀
대조로 재확인됐다. `actual_trade` 주 소스를 공식 API로 채택하는
8.4절의 권장을 그대로 유지한다.
