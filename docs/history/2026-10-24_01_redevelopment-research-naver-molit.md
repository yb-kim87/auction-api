## 배경 / 요청

"대림동 680 매물 분석" 엑셀처럼, 관심(★) 경매물건이 속한 **같은 재개발 구역 안**의 ①네이버 매매 호가
②국토부 실거래를 자동으로 모아 공시가 → 전세가(공시가 × 126%) → 호가/실매도 대비 갭까지 한 표로 보고 싶다.

사용자 지시(요약):
1. 네이버 구조는 **samsam 프로젝트를 최대한 그대로** 따라 만들 것 (samsam에서 잘 운영 중이므로). 앞으로도 이 규칙 유지.
2. **서버(Railway, auction-api)에서** 진행.
3. 같은 재개발 구역 안 매물은 **전부** 가져오고 **정보도 전부** 수집.
4. 실거래는 **최근 1년**만, 정보도 전부 수집.

## 동작

1. 경매물건 좌표 → 가장 가까운 재개발 구역(경계 오차 포함, 같은 구) 결정.
2. 구역 경계 샘플 점이 걸치는 법정동을 카카오로 확인(구역이 두 동에 걸칠 수 있음 — 예: 대림동 680 = 대림동+신길동).
3. **실거래**: 국토부 연립다세대 API(`MolitTradeClientService.fetchVillaTrades`)로 ~~최근 12개월 전체~~ → **현재는 최신 달부터 거슬러 올라가며 유효 거래 10건이 찰 때까지**(아래 "실거래 수집 방식 변경") × 시군구 → 해당 동만 → 지번별 카카오 좌표 → 구역 경계 거리 ≤ 100m만 저장(해제 거래는 `isCancelled`로 표시, 원본은 `rawJson`).
4. **네이버**: 동 코드별 목록 페이지(최대 30쪽) → 매물 좌표로 구역 경계 거리 ≤ 100m만 저장(목록 원본 `rawListJson`). 이어서 가까운 순으로 **상세 최대 40건/회**(`naverDetailRemaining`이 남으면 같은 버튼 "이어서 수집"). 상세 3회 연속 실패 시 중단(차단 의심).
5. 화면의 경계 오차범위(0~100m)는 **저장된 원본을 다시 거르기만** 한다(네이버 재호출 없음).
6. **공시가**: `housing_official_price`에서 법정동코드+본번/부번(4자리·비패딩 모두) → 호수 일치 > 층+면적(±0.6㎡) > 면적 순으로 추정. 근거를 화면에 표시.

## samsam 규칙 준수 (네이버 rate-limit)

- 모든 호출은 직렬 큐 + 랜덤 간격, 장시간 규칙적 패턴 회피를 위해 **1회 실행 상세 40건 상한**.
- 한 번 가져온 원본 저장 → 재필터. 오차범위 변경·화면 열기는 네이버를 호출하지 않는다.
- 수집 완료된 실행에서만 `missCount` 증가(실패한 실행이 정상 매물을 "사라짐"으로 만들지 않음).
- 진행 로그/상태(`redevelopment_research_runs.phase`)를 남긴다. 재배포로 끊겨도 자동 재개하지 않는다.
- 동시에 한 구역만 조사.
- 로컬 시험용으로만 `REDEV_RESEARCH_MAX_LIST_PAGES`, `REDEV_RESEARCH_DETAIL_LIMIT` 환경변수로 상한을 더 낮출 수 있다(운영은 기본값).

## 검증

- tsc 통과, Nest DI 부팅 확인(sqljs), 흐름 시험(sqljs): 구역→동 판별(대림동+신길동), 경계 거리 필터(먼 매물/지번 제외), 해제 거래 표시, 공시가 추정(대림동 680-6 503호 = 21,500만원, 엑셀 값과 일치).
- **네이버 실응답 확인(2026-10-24, 총 7건 호출: 토큰 1·동 코드 1·목록 2·상세 3)**: 이식 코드가 토큰 워밍업 → 동 코드(대림동 `1156013300`, 카카오 b_code와 동일) → 빌라 매매 목록(20건/쪽, `isMoreData`) → 상세까지 정상 동작. 확인된 실제 구조와 그에 맞춰 고친 점:
  - 목록: 20건 모두 `latitude/longitude`(문자열), `tagList`(방 수·연식 배지), `floorInfo`("중/7"처럼 숫자가 아닐 수 있음), 면적 `area1/area2`는 **정수로 반올림**. 한 동 목록에 단독/다가구(11)와 빌라(9)가 섞여 나옴 → 화면에 유형 필터 추가.
  - 상세: `articleDetail.pnu`(19자리 = 법정동코드10+대지구분1+본번4+부번4)로 지번/법정동코드를 정확히 얻음(카카오 역변환보다 우선), `exposureAddress`는 빌라는 지번까지·단독/다가구는 동까지, `roomCount/bathroomCount/householdCount/parkingCount`, **사용승인일은 `articleFacility.buildingUseAprvYmd`**(기존 코드는 `articleDetail`만 봐서 항상 null이었음 → 수정, 준공연도는 앞 4자리), **정확한 면적은 `articleSpace.exclusiveSpace/supplySpace`**(공시가 면적 매칭에 사용), **현 전세 보증금은 `articlePrice.allWarrantPrice`**(매물 설명의 "갭 1.3억"과 일치 → 실제 갭 계산에 사용). 마이그레이션 `1784302000000`으로 컬럼 8개 추가.
  - 저장해 둔 실제 응답으로 파서 재검증(네이버 재호출 없음): 사용승인일→준공연도, 면적, PNU, 전세보증금, 사진 URL, 입주일 모두 정상.
- **국토부**: 시험 시점에 12개월 모두 429(키 호출 한도 소진 추정, 부가세 계산기·매도분석과 키 공유)라 실응답 대신 모의 응답으로 로직만 검증했다. 서버에서 한도 오류가 나면 "일부 개월 실패"로 표시하고 다시 실행하면 보충된다(2개월 연속 429면 나머지는 시도하지 않고 중단).

## 배포 후 발견한 문제와 조치 (2026-10-24)

- **카카오 키 없음**: 첫 조사가 "구역이 걸친 법정동을 찾지 못했습니다(카카오 지역 조회 실패)"로 실패. Railway 로그(`railway logs -s auction`)에 `KAKAO_REST_API_KEY 환경변수가 설정되어 있지 않습니다`가 반복. `auction` 서비스에는 카카오 관련 환경변수가 하나도 없었다(코드의 `webinar-auth.service.ts`가 같은 이름을 읽지만 서버엔 설정돼 있지 않았음 — "로그인이 이미 쓰는 키"라는 가정이 틀렸다). 화면(Vercel)이 쓰는 같은 카카오 REST 키를 사용자 승인 하에 Railway `auction`에 `KAKAO_REST_API_KEY`로 등록(`railway variable set --stdin`, 값은 화면/명령줄에 노출하지 않음). 오류 문구에는 이제 카카오 호출 실패 원인(키 없음·권한·HTTP 상태)이 같이 표시된다.
- **국토부 키 한도 공유**: 기존 재판매 매칭 배치(`ResaleMatchService.runOnce`)가 서버 시작 60초 뒤와 2시간마다 아파트·빌라·오피스텔 실거래를 수집 대상 전 시군구 × 최대 36개월로 돈다. 로그에 국토부 429가 대량으로 찍히며 같은 키(`BUILDING_REGISTER_API_KEY`)의 호출 한도를 소진한다. 이 조사의 실거래 수집도 같은 키라 한도가 찬 시간대엔 "일부/전체 개월 조회 실패"가 날 수 있다. **서버를 재배포할 때마다 이 배치가 다시 돈다는 점도 유의.** 근본 해결은 data.go.kr 활용신청 한도 상향 또는 배치 범위 축소(이번 작업 범위 밖).

## 실거래 수집 방식 변경 + 용도 특정 (2026-10-25, 사용자 요청)

- **실거래는 "최근 1년 이내에서 가장 최근 거래부터 N건 샘플"**: 12개월 전체를 받던 것을, 이번 달부터 과거 순으로 한 달씩 조회하며 구역 안(경계 오차 포함) 유효(해제 아님) 거래가 N건이 되면 즉시 멈춘다. 기본 N=10(`TRADE_SAMPLE_LIMIT`, 시험용 `REDEV_RESEARCH_TRADE_LIMIT`로 조절), 점차 늘려 간다. 해제 거래는 저장은 하되 개수에는 세지 않는다. 한 달 응답에서 N건이 차면 국토부 호출이 1~2번으로 끝난다.
- **용도는 빌라**: 다세대·연립주택·도시형생활주택(경매코치도 이 셋을 propType "빌라"로 묶음). 네이버는 `VL`만 요청, 국토부는 연립다세대 API + 응답 `houseType`이 다세대/연립/도시형(또는 비어 있음)일 때만 통과, 경매물건은 propType "빌라"만 지도·목록·좌표 채우기 대상. 실제 영등포구 2026-09 응답의 houseType 분포는 다세대 63·연립 3(도시형생활주택은 다세대에 묶여 옴).
- 국토부 응답의 `houseType`·`estateAgentSggNm`을 정규화하며 버리던 것을 보존(`MolitTradeItem` 선택 필드 추가, 기존 기능 영향 없음)하고, 저장하는 `houseType`도 고정값 "RH" 대신 실제 값으로 바꿨다.

## 다세대(DSD) 누락 수정 (2026-10-25)

- 증상: 엑셀에는 있는 호가(대림동 685-5, 5층 51.31㎡ 6.5억)가 조사 결과에 없었다. 구역 안(경계 0m), 좌표도 정상인데 빠졌다.
- 원인: 네이버가 이 매물을 `DSD:다세대`(articleRealEstateTypeCode A06 "빌라단지-다세대")로 분류하는데, 수집을 빌라(`VL` = C03 빌라/연립)만 요청하도록 좁혀서 다세대가 통째로 제외됐다. 사용자가 준 fin.land 링크의 `layer` 값(lz-string 압축 JSON, `article_detail` → `articleId` 2652040016)을 풀어 매물번호를 얻고, 1건 상세 조회로 확인했다.
- 수정: 요청 유형을 `VL:DSD`로(상수 `VILLA_REAL_ESTATE_TYPES`), 응답 유형 안전 필터도 VL·DSD 둘 다 통과. 실제 호출 1쪽: VL 12 + DSD 8.
- 참고: 위치 비공개(`isLocationShow=false`) 매물은 상세에 PNU가 없고 주소가 동 단위까지만 나온다(`exposureAddress` = "서울시 영등포구 대림동"). 이때 지번·공시가는 좌표 → 카카오 지번 변환으로 채운다(해당 매물 좌표는 685-5 지번의 카카오 좌표와 약 10m 이내로 일치). 도시형생활주택이 네이버에서 따로 분류되는지는 아직 확인하지 못했다(필요하면 해당 유형 코드를 추가).

## 공시가 추정: 지하층 처리 + 근거 표시 (2026-10-25)

- 증상: 실거래 중 `-1층`(지하/반지하)과 일부 `1층` 건이 "층+면적 추정"이 아니라 "면적 추정"으로 표시됐다.
- 원인: 층 매칭 코드가 층이 양수일 때만 동작했고(`floor > 0`), 공시가 호 이름이 `B…`로 시작하면 층을 계산하지 않았다 → 지하층은 항상 면적만으로 추정. 1층 건은 면적이 맞는 호 중 "호 이름에서 읽은 층이 1인 호"가 없을 때(호 이름이 `1호`·`01`처럼 3자리 미만이거나 같은 면적 1층 호 없음) 같은 결과.
- 수정: 호 이름이 `B…`/`지하…`/`지층…`이면 층 -1로 인식하고, 지하(-1)도 층 매칭 대상에 포함. 층을 읽을 수 없는 호 이름 형태는 그대로 면적 추정(정직하게 표시).
- 추가: 추정 결과에 근거 후보(`rows`: 호·동·면적·공시가·읽은 층·실제 사용 여부)와 건물 공시가격 총 호수(`buildingRowCount`)를 포함하고, 화면에서 호가/실거래 행을 펼치면 "공시가 추정 근거"로 보여준다(면적이 안 맞으면 면적이 가까운 호 8개).

## 공시가 층 매칭 보강 + 표 정리 (2026-10-25)

- **공시가 호 이름 형식(로컬 공시가격 CSV 실측 — `.playwright-mcp/yeongdeungpo_2026.csv`)**: 건물마다 호 이름이 다르다. 대림동 686-9 장미빌라 = `1층201`·`2층301`·`지층 101`(층이 앞에 명시), 680-13 유진빌라 = `1층비`·`2층에이`·`지층 비`, 684-7/685-5/680-6/691-4 = `201`·`301`처럼 3자리. 기존 `floorOfHo`는 숫자만 모아 `1층201`→`1201`→12층으로 잘못 읽었고 `1층비`는 숫자가 1자리라 읽지 못해 "면적 추정"으로 떨어졌다.
