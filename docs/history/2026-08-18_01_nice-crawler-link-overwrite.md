# 2026-08-18_01 나이스크롤러가 기존 물건의 "경매지 정보" 링크를 덮어쓸 수 있던 문제

## 배경

사용자 신고: "2025타경20957 이물건 보고있는데 경매지 정보가 나이스옥션으로
연결되던데 이건 왜그러는거지?? 탱크옥션으로 안되고?"

## 조사 결과

두 가지를 확인했다.

### 1) 일반적인 원인(재발 가능한 버그) — 수정함

탱크크롤러와 나이스크롤러(`nice-crawler`)는 같은 저장 파이프라인
(`AuctionsService.importCrawledItem` → `upsertOne` →
`mergeAuctionFromSource`)을 공유한다(2026-08-07, `crawl-item-validation.util.ts`
주석 참고). 매칭은 사건번호(`auctionNo`) 기준으로 이뤄지는데, `link` 필드
병합 시 `pickStringWithOptions`가 "새 값이 비어있을 때만 기존 값 유지"
로직만 갖고 있어서, 나이스크롤러가 **이미 탱크옥션 링크가 있는 기존
물건**을 같은 사건번호로 재수집하면 그 물건의 `link`를 니이스옥션 링크로
덮어써 버렸다 — "경매지 정보" 버튼(`AuctionDetailModal.tsx`의
`preview.link`)이 니이스옥션으로 뜨는 원인이 될 수 있는 구조였다.

**수정**: `auction-builder.ts`의 `MergeOptions`에 `preserveLinkIfExists`
추가 — 켜져 있으면 기존 `link`가 이미 있을 때 새 값으로 덮어쓰지 않고
그대로 유지(빈 경우에만 채움). `AuctionsService.importCrawledItem`에서
`submittedBy === "nice-crawler"`일 때만 이 옵션을 켜서 `upsertOne`에
전달 — 탱크크롤러 갱신 흐름은 기존 동작 그대로 유지.

### 2) 이번에 신고된 특정 건(2025타경20957)은 다른 이유

DB를 직접 조회해보니 이 물건은 **2026-08-06 최초 생성 시점부터 지금까지
한 번도 갱신된 적이 없다**(`auction_change_logs`에 이 물건 관련 이력
0건, `updatedAt` null). 즉 탱크옥션 링크가 있었다가 나이스크롤러가
덮어쓴 게 아니라, **애초에 탱크옥션에서는 아직 이 사건을 수집하지
못했고 나이스크롤러가 단독으로 최초 수집해 들어온 물건**이라 링크가
니이스옥션으로만 존재하는 것이었다. 이 건 자체는 되돌릴 "이전 탱크
링크"가 없어 복구 대상이 아니다 — 탱크옥션이 이 사건을 수집하면
자연스럽게 탱크 링크로 채워진다(또는 관리자가 물건 상세에서 직접
링크를 수정할 수 있음).

## 결과
- 타입체크·빌드 통과.
- Railway 배포 후 상태 확인(아래 섹션 참고).
- 앞으로는 나이스크롤러가 기존 탱크 링크를 덮어쓰는 일은 없다 — 다만
  이미 이 문제로 링크가 바뀌어버린 과거 건이 더 있을 수 있는데, 그건
  `auction_change_logs`에 `field`별 이력이 없어(변경 diff가 JSON
  `changes` 컬럼에 뭉쳐 있음) 일괄 탐지가 쉽지 않다 — 필요하면 개별
  신고 시 그때그때 DB를 직접 조회해 확인하기로 함.
