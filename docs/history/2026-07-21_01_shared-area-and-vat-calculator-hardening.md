# 2026-07-21 공용면적(sharedArea) 수집 및 부가세계산기 고도화

## 배경

부가세계산기(85㎡ 초과 아파트 대상)가 건물기준시가를 계산할 때 전용면적만 쓰고 있어
정확도가 떨어졌다. 탱크옥션 물건상세 페이지의 "건축물정보" 탭에는 공용면적이 표시되지만,
크롤러가 이 값을 저장하지 않고 있었다.

## 실행한 작업(요약)

1. **탱크옥션 공용면적 조사**: `AuctView.php` 응답의 `bldgInfo.tot_shr_sqm`은 항상 0으로
   비어있음을 실측 확인. 대신 탱크옥션 내부 API `POST /ca/res/getEnvBldg.php`
   (파라미터: `baseInfo.apiBldgTitle_Pk`, `apiBldgRecap_Pk`, `landInfo.items[0].pnu`)가
   공용면적(`dfInfo`의 `totPbArea`)을 제공함을 확인. 이 데이터의 원본은 공공데이터포털
   건축물대장(`getBrExposPubuseAreaInfo`)과 동일.

2. **크롤러 반영**: `crawler/tank_detail.py`에 `fetch_env_bldg`/`parse_exclusive_area_from_env_bldg`
   추가(Selenium), `crawler/http_client.py`에 동일 기능의 httpx 버전 추가(`full_httpx_worker.py`,
   `parsers.py`에도 반영). `item_crawl.py`에서 `raw_detail` 확보 직후 `sharedArea`를 채워 최종
   payload에 포함.

3. **DB/백엔드**: `auctions.sharedArea` 컬럼 추가(마이그레이션
   `1784233000000-AddAuctionSharedArea.ts`), 엔티티/DTO/매퍼/빌더 전체 연결.
   **버그 발견 및 수정**: `AUCTION_FIELD_LABELS`(auction-change.util.ts)에 `sharedArea`를
   빠뜨려 `buildFieldChanges`가 변경을 감지 못해 저장이 조용히 스킵되는 문제 — 필드를
   추가하는 신규 마이그레이션 시 이 목록 등록을 잊으면 저장 자체가 안 되니 주의.

4. **기존 물건 재크롤 없는 보정**: 전체 재크롤 대신 `/crawler/missing-shared-area`
   (대상 조회, 85㎡ 초과 아파트 중 sharedArea 비어있는 물건),
   `/crawler/import-shared-area`(단일 필드 patch) API를 신설하고
   `crawler/backfill_shared_area.py` 스크립트로 245건 중 213건 채움(32건은 탱크옥션 자체에
   건축물대장 데이터 없음).

5. **부가세계산기 성능 개선**: DB에 `sharedArea`+`builtYear`가 이미 있으면 건축물대장 API
   (`fetchVatBuildingRegister`, 간헐적 빈 응답으로 최대 3회×2 재시도하던 가장 느린 구간)
   조회를 생략하고 DB 값으로 바로 계산하도록 `ProfitCalculatorPanel.tsx` 수정.

6. **계산식 노출 방지**: 부가세 계산 로직(`vat-calc.ts`, 국세청 고시 지수표·잔가율 산식·
   안분 공식)이 클라이언트 JS 번들에 그대로 포함되어 개발자도구로 열람 가능한 문제 발견
   (프로덕션 빌드로 실측 확인). 계산을 `/api/vat/calc` 서버 라우트로 이전하고 클라이언트는
   원자재 값(landArea, landPricePerM2, buildingArea, builtYear, salePrice)만 보내 결과만
   받도록 변경. `/search` 페이지 청크에서 계산 상수가 완전히 사라짐을 재확인.
   (참고: 관리자 전용 `CrawlerVatTab.tsx`는 계산 과정을 화면에 보여주는 게 의도된 기능이라
   그대로 유지 — admin만 접근 가능해 노출 위험 낮음)

7. **부가세 표시 방식 변경**: 기본값을 최저가 → 정상가(시가)로 변경, "부가세 최저가로 표시"
   체크박스 추가.

8. **UI 개선**:
   - 물건 상세 "토지지분"에 ㎡ 단위 표시, `sharedArea` 있으면 "(공용 N㎡)" 병기 —
     단, **공용면적 병기는 관리자 전용**(`isAdmin` 체크, 일반 사용자에게는 미노출).
   - 부가세 입력/자동계산 블록을 주황 계열 배경+테두리로 하이라이트 처리(눈에 잘 띄도록).

## 오피스텔 취득세/부가세 특례 반영 (2026-07-23 追記)

사용자 요청: 오피스텔은 취득세가 주택 취득세 체계(무주택/다주택 중과 등)와 무관하게
건물분 4%+지방교육세 0.4%+농특세 0.2%=4.6% 단일세율이고, 부가세도 면적(85㎡)과
무관하게 항상 부담이 발생하는데 수익계산기가 이를 반영 안 하고 있다는 지적.

- `src/lib/profit-calculator.ts`: `isOfficetel(usage)`(usage 문자열이 "오피스텔"로
  시작하는지 판정) 신규. `acquisitionTaxRate()`에 `usage` 파라미터 추가 — 오피스텔이면
  무주택/다주택 로직을 건너뛰고 `OFFICETEL_ACQUISITION_TAX_RATE = 0.046`을 바로 반환.
  `acquisitionTaxBracketLabel()`도 오피스텔이면 "오피스텔(4.6% 고정)" 표시.
- 부가세 대상 판정(`over85`)도 `isOver85Sqm(area) || isOfficetel(usage)`로 OR 조건
  확장 — 오피스텔은 면적과 무관하게 항상 부가세계산기 UI(자동계산 버튼 등)가 노출됨.
- **부가세 용도지수 버그 발견**: `/api/vat/calc`(서버 계산 라우트)가 물건의 실제 usage와
  무관하게 항상 `APARTMENT_USAGE_INDEX = 110`(아파트 지수)으로 고정돼 있었음. 참고
  서비스 atomtax-app(https://atomtax-app.vercel.app/calculator/vat/calc)을 Selenium으로
  실측(주거용/상업용 카테고리 토글 클릭 후 각각의 "용도" 드롭다운 옵션 비교) 결과,
  오피스텔은 두 카테고리 어디에 있든 용도지수가 동일하게 **140**임을 확인(카테고리
  토글은 옵션 목록을 필터링하는 UI 기능일 뿐, 계산 파라미터 자체를 바꾸지 않음) —
  관리자 전용 `CrawlerVatTab.tsx`에는 이미 이 140 값이 있었는데(주석: "시행령상
  업무시설로 분류되나 주거용 임대 편의를 위해 주거 카테고리에 추가, 지수는 동일") 수익
  계산 패널의 서버 라우트에는 반영이 안 돼 있었음. `usage`가 오피스텔이면 자동으로
  140을 쓰도록 수정 — 용도지수는 건물기준시가 계산식에 곱해지는 파라미터라, 110→140
  적용 시 건물기준시가가 약 1.27배 커지고 그에 비례해 건물 안분 부가세도 커진다(즉
  이전까지는 오피스텔 부가세가 실제보다 낮게 계산되고 있었음).
- `fetchVatCalc()`/`ProfitCalculatorPanel.tsx`/`estimateDefaultProfit()`(목록 카드
  "추정 수익" 요약값 계산)까지 전부 `usage`를 전달하도록 연결.
- 프로덕션 빌드로 재검증: 오피스텔 계산 상수(`OFFICETEL_USAGE_INDEX` 등)가 `/search`
  (일반 사용자) 청크에는 없고 `/admin`(관리자, CrawlerVatTab) 청크에만 있음을
  확인 — 기존에 구축해둔 "부가세 계산식 클라이언트 비노출" 방침이 새 로직에도 유지됨.

## 관리자 부가세계산기 상업용 옵션 미작동 + 구조지수 자동 매칭 (2026-07-23 追記)

오피스텔 취득세/부가세 작업 도중 사용자가 관리자 부가세계산기(`CrawlerVatTab.tsx`)의
"상업용" 버튼을 눌러도 아무 반영이 안 된다고 지적 — 확인 결과 `usageType`(주거용/
상업용) state는 있었지만 용도 드롭박스(`USAGE_OPTIONS`, 항상 아파트/기타/오피스텔
3개 고정)가 이 state를 전혀 참조하지 않는 버그였음(구현 자체가 누락된 상태).

atomtax-app.vercel.app(https://atomtax-app.vercel.app/calculator/vat/calc)을
Selenium으로 재실측:
- 상업용 용도 옵션 40개(호텔·백화점·사무소·병원·학교 등) 전체 확보, 확인 완료.
- 구조 드롭박스는 주거용/상업용 공통으로 동일한 목록(24개)임을 확인 — 카테고리별로
  분리할 필요 없음.
- atomtax는 **용도** 옵션 라벨엔 지수를 표시하지만(`오피스텔 (주거용 임대) (140)`),
  **구조** 옵션 라벨엔 지수를 표시하지 않음(`철근콘크리트조 (RC)`만) — 우리 화면은
  구조에도 `(지수)`를 붙이고 있어 atomtax와 동일하게 구조 라벨에서만 지수 표시 제거.

`CrawlerVatTab.tsx` 수정: `RESIDENTIAL_USAGE_OPTIONS`(기존 3개)/`COMMERCIAL_USAGE_
OPTIONS`(신규 40개)로 분리, `usage` state를 문자열 대신 "선택된 인덱스"로 바꿔
카테고리 전환 시 `usageOptions[usageOptionIndex]`로 실제 옵션이 함께 바뀌도록 연결
(`handleUsageTypeChange`가 토글 시 인덱스를 0으로 리셋).

### 구조지수 자동 매칭 (수익계산기 `/api/vat/calc`)
논의 중 "구조가 바뀌면 계산식이 어떻게 달라지냐"는 질문에서, 현재 수익계산기
서버 라우트가 구조지수를 항상 `STRUCTURE_INDEX_RC=100`(철근콘크리트조) 고정으로
계산하고 있음을 재확인. 건축물대장 자동조회 API(`fetchVatBuildingRegister`)가
이미 `structureName`(공공데이터포털 표준 구조코드명, 예: "철근콘크리트구조")을
받아오고 있었지만 그동안 버려지고 있었음(기존 주석: "계산기 구조 select와 표기가
달라 매칭은 안 되지만 참고용으로 표시").

- `src/lib/vat-calc.ts`: `STRUCTURE_TABLE`(국세청 고시 구조지수·잔가율 그룹표,
  `CrawlerVatTab.tsx`의 `STRUCTURE_OPTIONS`와 동일 데이터) + 각 구조별
  `keywords`(strctCdNm 매칭용 부분 문자열, 예: "철근콘크리트", "SRC", "경량철골")
  추가. `matchStructureIndex(structureName)`으로 매칭, 실패 시 null(호출자가
  RC/100/내용연수50으로 폴백).
- `/api/vat/calc`가 `body.structureName`을 받아 매칭 시도, 매칭되면 지수뿐 아니라
  잔가율 그룹(depGroup, 내용연수)도 함께 구조에 맞게 적용.
- 클라이언트(`fetchVatCalc`, `ProfitCalculatorPanel.tsx`)에 `structureName` 전달
  경로 연결 — 단, `skipBuildingRegister`(DB에 이미 sharedArea+builtYear 있어
  건축물대장 API 자체를 생략하는 경로)일 때는 구조명을 못 얻어 `null`(RC 폴백).
- 프로덕션 빌드로 재검증: `STRUCTURE_TABLE`/`matchStructureIndex`가 `/search`
  청크에는 없고 서버 전용으로 유지됨(기존 "계산식 클라이언트 비노출" 방침 유지).

## 동 없는 건물(오피스텔·상가) 건물면적 오조회 버그 (2026-07-23 追記)

사용자가 atomtax-app(https://atomtax-app.vercel.app/calculator/vat/calc)에 같은
주소(경기 안양시 만안구 전파로24번길 32, 201호)를 넣고 자동조회한 결과(건물 면적
80.00㎡, 동 201의 전유 66.69㎡+공용 13.31㎡ 자동 합산)와, 우리 관리자 부가세계산기의
결과(건물 면적 **1178.61㎡**)가 완전히 다르다고 스크린샷으로 지적.

### 원인
`src/app/api/vat/building-register/route.ts`가 `if (dong && ho)`일 때만 전유부
(`getBrExposPubuseAreaInfo`, 정확한 호별 면적) 조회를 시도하고, 동이 비어있으면
무조건 표제부(`getBrTitleInfo`, 단지/건물 전체의 여러 동·부속건물이 순서 보장 없이
섞인 목록)의 **첫 항목**(`rows[0]`)으로 폴백하던 구조. 이 물건은 "동" 개념이 없는
단일 건물(오피스텔/상가류로 추정)이라 사용자가 상세 위치에 "동"을 입력하지 않았고
(스크린샷에도 동 칸이 빈칸), 그래서 매번 이 표제부 폴백 경로를 타 부정확한 값(단지
전체 합산으로 보이는 1178.61㎡)이 나왔음.

### 수정

## 2026-07-23 追記 3: 부가세 결과값이 atomtax-app과 미세하게 다르던 반올림 단위 버그

### 문제
사용자가 동일 입력값(매도예상가 253,000,000원, 토지 27.42㎡, 토지공시지가

나란히 비교 — 부가가치세 최저가(8,310,000원)는 일치했지만 나머지 3개
(부가가치세 시가, 건물가액, 토지가액)가 미세하게(2만원 이내) 어긋남.

### 원인 (atomtax-app 결과값 역산으로 확정)
기존 `calcVat()`은 `vatMarket`(시가)과 `buildingAlloc`(건물가액)을 모두
"만원 단위"로 반올림했는데, 실제로는 항목마다 반올림 단위가 다름:
- `vatMarket`(부가가치세 시가): **원 단위** 반올림(소수점만 정리, 만원
  단위 아님) — `11,867,996.89` → `11,867,997`
- `buildingAlloc`(건물가액, 분배 후): **십만원 단위** 반올림 —
  `83,075,978.2` → `83,100,000`(기존 만원 단위였다면 `83,080,000`으로
  2만원 낮게 나옴)
- `vatLow`(부가가치세 최저가): 만원 단위 반올림(기존과 동일, 그래서 이
  항목만 우연히 일치했었음)

### 수정
`vat-calc.ts`의 `calcVat()`에서 `vatMarket`은 `Math.round()`(원단위),
`buildingAlloc`은 `roundToUnit(value, 100000)`(십만원 단위)로 분리.
`CrawlerVatTab.tsx`가 자체 구현하던 계산 로직(로컬 `roundToManWon` 포함)을
전부 제거하고 `vat-calc.ts`의 `calcVat()`을 재사용하도록 통합 — 이 계산식은
이제 한 곳(vat-calc.ts)에만 존재.

### 검증
`calcVat({salePrice:253000000, landArea:27.42, landPricePerM2:2920000,
buildingStandardPrice:77600000})` → `{landAlloc:161590000,
buildingAlloc:83100000, vatLow:8310000, vatMarket:11867997}` — atomtax-app
스크린샷 4개 값과 정확히 일치. 타입체크 통과, 커밋 `68f4584` 배포 완료.

### 교훈
- "최종 결과가 만원 단위로 딱 떨어진다"는 이전 실측 결론(주석에 남아있던
  `roundToManWon` 주석 근거)이 우연히 일부 케이스에서만 맞았던 것 —
  중간 계산 단계별로 각각 다른 반올림 규칙을 쓸 수 있다는 점을 이번에
  여러 항목을 동시에 대조해서야 발견함. 이런 서드파티 계산기의 반올림
  규칙은 단일 결과값이 아니라 여러 출력 필드를 동시에 놓고 역산해야
  정확히 특정할 수 있음.

## 2026-07-23 追記 4: 동 표기 없는 지번주소(오피스텔 등) 물건의 자동계산 실패

### 문제
물건 상세(수익계산기)에서 "2025타경511215"(인천 미추홀구, 오피스텔) 물건의

도로명주소가 없는 지번주소이고, "동" 표기 없이 "N층M호"만 있는 형식.

### 원인
1. `parseAuctionAddress`의 지번주소 처리 로직(`beforeDongMatch`)은
   "NNN동" 패턴이 있어야만 그 앞부분을 잘라냈는데, 이 주소엔 그 패턴이

2. `address-to-coord` 라우트가 `type=ROAD`로만 조회했는데, 지번주소를

3. 위 두 문제가 겹쳐 실측: 건물명/층/호가 남은 원본 문자열로 ROAD 조회

   `status: OK`, 게다가 `level4LC`에 19자리 PNU가 이미 완성된 형태로
   반환됨(`"2817710200106300070"`) — 역지오코딩 단계 없이 바로 활용 가능.

### 수정
- `address-parse.ts`: "동" 패턴이 없으면 지번(숫자-숫자) 뒤에 남은

## 2026-07-23 追記 5: 공동주택(아파트/연립·다세대) 용도 매칭 오류

### 문제
사용자가 "2025타경511215"(인천 미추홀구 용현동 630-70, 모던하우스)
물건을 우리 시스템과 atomtax-app에서 나란히 돌려본 결과, atomtax-app은
용도를 "아파트(110)"로 분류했는데 우리는 "단독·다세대·연립·기숙사 등
(100)"으로 자동 매칭돼 부가세 결과가 달랐음.

### 원인
건축물대장 API의 `mainPurpsCdNm`은 아파트와 연립·다세대주택을 구분하지
않고 둘 다 **"공동주택"**으로만 표기한다(실측 확인: 이 물건은
`mainPurpsCdNm="공동주택"`, `grndFlrCnt=6`, `hhldCnt=6`). 기존
`matchUsage()`는 키워드 "공동주택"을 무조건 "단독·다세대·연립·기숙사
등(100)"에 매칭했는데, 건축법 시행령상 실제 기준은 **층수**다 —
5개층 이상이면 아파트, 4개층 이하면 연립·다세대. 이 물건은 6층이라
"아파트"가 맞고, atomtax-app의 분류가 정확했음.

### 수정
`vat-calc.ts`의 `matchUsage()`에 `groundFloors`(지상층수) 파라미터를
추가. `mainPurpsCdNm`이 "공동주택"이고 층수 정보가 있으면 5층 이상은
아파트(110), 4층 이하는 기존대로 단독·다세대·연립 등(100)으로 분기.
`building-register` 라우트가 표제부의 `grndFlrCnt`를 응답에 포함하도록
확장하고, `CrawlerVatTab.tsx`의 `matchUsage()` 호출부에 전달.

### 검증
`matchUsage("공동주택", 6)` → 아파트(110), `matchUsage("공동주택", 3)`
→ 단독·다세대·연립 등(100), 층수 정보 없을 때는 기존과 동일하게
100으로 보수적 폴백(회귀 없음). 타입체크 통과, 커밋 `d46af48` 배포
완료.

### 별개로 확인한 사항 → 追記 6에서 해결
물건 상세(`ProfitCalculatorPanel.tsx` → `/api/vat/calc` 라우트)는
`matchUsage()`를 아예 쓰지 않고, 탱크옥션 크롤링 `usage` 필드로
오피스텔 여부만 판별해 오피스텔이 아니면 무조건 아파트(110)로
고정한다 — 즉 이번 층수 기반 아파트/연립·다세대 구분은 관리자
부가세계산기에만 적용됐고, 물건 상세 자동계산에는 반영되지 않았음.
아래 追記 6에서 실제로 이 문제가 재현되어 해결함.

## 2026-07-23 追記 6: 물건 상세 부가세 자동계산도 탱크옥션 usage 텍스트에
의존해 같은 물건에서 재발

### 문제
사용자가 물건 상세(수익계산기) 화면에서 追記 4의 같은 물건("2025타경

탭에서는 追記 5로 이미 고쳤는데 물건 상세에서 같은 증상이 재발.

### 원인
바로 위(별개로 확인한 사항)에 적어둔 대로, `/api/vat/calc` 라우트가

를 저장해 `/api/vat/calc` 호출 시 함께 전달하도록 확장. 서버 라우트는
이 값이 있으면 `matchUsage()`로 정확히 판정하고, 없으면(DB에 이미

불일치가 생기면 화면만 보고 바로 원인 후보를 좁힐 수 있음.

같은 입력값(매도가 202,000,000원, 토지 22.82㎡, 공시지가 1,392,000원/

## 2026-07-23 追記 7: 물건 상세 상단 배지가 오피스텔을 "아파트"로 표시

### 문제
사용자가 "2025타경511686"(인천 부평구 부평동 417-17, 해피애버) 물건을
확인하며 목록 카드엔 "오피스텔(주거)" 배지가 정확히 나오는데, 물건
상세 모달 상단 배지는 "아파트"로 나오는 불일치를 발견.

### 원인
물건 상세 모달의 배지는 `item.usage`가 아니라 `item.propType`
("아파트"|"빌라" 둘 중 하나)을 표시하는데, `propType`은
`address-parser.ts`의 `parseAddressMeta()`가 **주소 문자열**에
"빌라/연립/다세대/다가구" 키워드가 있는지만 보고 판정한다 — 오피스텔
이라는 카테고리 자체가 이 함수에 없어 해당 키워드가 없으면 무조건
"아파트"로 기본값이 잡혔다. 목록 카드는 별도로 `usage` 필드를 직접
표시해서 정확했던 것.

### 수정 (auction-api)
`parseAddressMeta(address, usage)`로 시그니처 확장 — `usage` 필드가
있으면 주소 문자열보다 우선 신뢰: `usage`에 "오피스텔"이 포함되면
`propType="오피스텔"`, 빌라류 키워드가 포함되면 `"빌라"`, 그 외
`"아파트"`. `usage`가 없는 호출부(예: 마이그레이션성 재계산)는 기존
주소 텍스트 판정으로 자동 폴백해 회귀 없음. `auction-builder.ts`,
`auctions.service.ts`의 호출부 2곳에 `usage` 인자 추가.

### 수정 (auction 프론트)
`AuctionItem.propType` 타입에 `"오피스텔"` 값 추가. 검색 필터
(`property-type-options.ts`)는 이미 `usage` 필드 기반으로 판정하고
있어 이번 propType 변경과 무관하게 정상 동작함을 확인(코드 주석에도
"propType은 주소 키워드 추론이라 오분류 가능"이라고 이미 경고돼
있었음).

### 검증
타입체크(프론트/백엔드 모두) 통과. 커밋: auction `c16703e`, auction-api
`85ad33c`.

### 추가 수정 — 근본 해결(추가 커밋 `6d8e294`)
위 수정을 배포한 뒤에도 사용자가 같은 물건("2025타경511686")을 다시
열어보니 여전히 "아파트"로 나옴을 확인 — `propType`은 **크롤링 시점에
계산되어 DB에 저장되는 값**이라, `address-parser.ts` 로직을 고쳐도
이미 저장된 기존 물건에는 소급 반영되지 않는다는 한계가 있었음(새로
크롤링되는 물건부터만 정확해짐).

사용자 지적: "리스트에 있는 값이 물건 상세에 그대로 나오게 하는건
안돼?? 왜 DB를 구분한거야? 어차피 같은 역할인데" — 정확한 지적. 목록
카드는 이미 `item.usage`를 직접 표시해 정확했고, 상세 모달만 별도
파생 필드 `propType`을 표시해서 문제가 생겼던 것. 굳이 파생 필드에
의존할 이유가 없어 `AuctionDetailModal.tsx`의 배지 2곳(데스크톱
썸네일 위, 모바일 헤더)을 `preview.usage || preview.propType`으로
변경 — usage가 있으면 그대로 쓰고, 없는 예외 케이스만 propType으로
폴백. 이제 기존 물건이든 신규 크롤링 물건이든, DB의 propType 값이
낡았든 상관없이 목록 카드와 상세 모달이 항상 같은 값을 보여줌.

### 교훈
- 같은 데이터를 화면마다 다른 파생 필드로 표시하면, 파생 로직을
  고쳐도 이미 저장된 데이터에는 소급 적용되지 않는 함정이 생긴다.
  "계산 로직을 고친다"보다 "애초에 파생 필드에 의존하지 않고 원본
  필드를 그대로 쓴다"가 더 근본적이고 데이터 상태와 무관하게 항상
  정확한 해결책이었음.

## 2026-07-23 追記 8: 세대수 많은 건물의 전유부 조회 누락 → 표제부 오폴백

### 문제
"2025타경511686"(인천 부평구 부평동 417-17, 403호)의 관리자
부가세계산기 건물 면적 자동조회가 **3434.88㎡**로 나왔는데,
atomtax-app은 **86.09㎡**(전유 74.79+공용 11.30)로 계산했음. 3434.88㎡는
건물 전체 총면적(표제부 `totArea`)과 거의 같은 자릿수라 "동/호 매칭

### 원인
건축물대장 전유부(`getBrExposPubuseAreaInfo`) API는 `numOfRows`를
크게 넣어도 한 페이지 최대 100건만 반환한다(실측 확인: `numOfRows=500`

기존 코드는 `numOfRows=50`(!), `pageNo=1` 고정으로 첫 페이지만 조회
했음. "403호"는 페이지 3에서야 나타나(직접 페이지네이션해 실측 확인),
1페이지만 보는 기존 로직은 이를 "동/호로 못 찾음"으로 오판해 표제부
(건물 전체 합산 면적)로 조용히 폴백했음.

### 수정
`building-register/route.ts`의 `fetchExposedOnce`를
`fetchExposedAll`로 교체 — 응답의 `totalCount`를 보고 남은 페이지를
전부 순회해 모든 전유부 행을 수집하도록 변경.

추가로 사용자 지적("표제부 값이 도출되면 차라리 조회 실패로 하자,
오해할 수 있겠어")을 반영해, `ho`가 지정됐는데 전유부에서 끝내 못
찾은 경우 표제부로 조용히 폴백하지 않고 명시적 404 실패로 바꿈 —
전유부(호실 단위, 수십~백여 ㎡)와 표제부(건물 전체, 수천 ㎡)는
자릿수가 완전히 달라, 조용한 폴백은 사용자가 "자동조회 완료"로
오인하고 잘못된 큰 값을 그대로 부가세 계산에 쓰게 만드는 위험이 있음.

### 검증
실제로 캡처한 3개 페이지(총 247건) 응답을 페이지네이션 로직 그대로
재현해 "403호" 필터링 → 전유(74.79㎡)+공용(1.18+0.33+0.89+8.8+0.1=
11.30㎡) = **86.09㎡**, atomtax-app과 정확히 일치. 타입체크 통과,
커밋 `c167ffa` 배포 완료.

### 교훈
- "50건이면 충분하겠지"처럼 페이지 크기를 가정하고 첫 페이지만 보는

## 2026-07-23 追記 9: 전체 등록 물건 3872건 주소 파싱 전수 점검

### 배경
追記 4, 8에서 개별 물건 단위로 주소 파싱 버그를 발견/수정하는 패턴이
반복되자, 사용자가 "이번 기회에 주소로 인한 오류가 발생하는 내용이
있는지 우리 등록된 물건들을 통해서 검토해보고 문제가 있는건 수정하자
... 정확히 안되는거 빼고 최대한 전유부들을 다 잘 가져오도록 검토"라고
요청 — 사후 대응 대신 전체 데이터로 선제 점검하기로 함.

### 방법
프로덕션 API(`GET /auctions`, 인증 불필요)로 전체 물건(3872건) JSON을
받아, `parseAuctionAddress()`를 그대로 시뮬레이션해 각 물건의 원본
주소에 "호"가 있는데 `ho`가 `null`로 추출되는 케이스를 전수 조사.
최초 결과 61건 실패.

### 발견한 패턴과 수정
1. **"도로명주소:" 케이스에서 dong/ho가 항상 유실** — 이 분기가
   `roadNameMatch`를 만나면 조기 return하면서 `dongHoMatch`가 애초에
   "동" 없는 "N층M호"는 못 잡는 구조였음(실측: "간석동 235-27
   2층202호 (도로명주소:...)"). 검색주소(도로명)와 dong/ho 추출을
   분리해 원본 지번 부분에서 항상 먼저 동/호를 뽑도록 재구성.
2. **층 표기 자체가 없이 "건물명 N호"만 있는 경우**(예: "현대로얄빌라
   제501호") — 동/층 매칭이 모두 실패했을 때만 시도하는 최종 폴백으로
   호수만 추출.
3. **호수 숫자 앞 한글 접두문자**(예: "3층비303호", "26층오2602호") —
   지하·별동 구분용으로 추정, 접두문자를 버리고 숫자만 호수로.
4. **"N층" 뒤 하이픈 연결 동/블록-호수**(예: "13층디-1313호", "14층
   102-1402호") — 하이픈 뒤 숫자를 호수로.
5. **건물동이 한글 순번/알파벳 음차인 경우**(예: "가동", "에이동")
   — 최초 구현은 임의의 한글 1글자를 전부 동으로 허용해 법정동명
   마지막 글자를 오탐(예: "치평동"의 "평", "정릉동"의 "릉", "장항동"의
   "항"을 건물동으로 잘못 추출). 실제 쓰이는 값(가~하, 에이/비/씨/디)
   만 화이트리스트로 제한해 오탐 0건 확인.

### 검증
전체 3872건에 대해 "원본에 호가 있는데 ho 추출 실패" 건수가 61건 →
**0건**으로 감소. 화이트리스트 적용 전 한글동 오탐(법정동명 글자를
동으로 잘못 인식) 여부도 전체 데이터로 재확인해 0건. 기존에 검증했던
모든 케이스(도로명 괄호 표기, N동 콤마 케이스, 하이픈 있는/없는 지번
등)도 회귀 없이 그대로 동작함을 재확인. 타입체크 통과, 커밋 `dc24c60`
배포 완료.

### 남은 한계 (별도 조치 불필요)
- 재개발지구 특유 표기(예: "남목1지구2블럭2롯트")처럼 표준 지번 형식이
  아닌 주소는 VWorld PARCEL/도로명 검색 어느 쪽으로도 좌표 변환이
  안 됨(실측 확인) — `parseAuctionAddress`가 해결할 수 있는 범위 밖의
  원본 데이터 특수성이라 "직접 입력해 주세요" 안내가 뜨는 게 정상.
- 주소 필드에 건물 구조 설명이 통째로 잘못 들어간 소수 건(예: `"*
  철근콘크리트조\n41.61㎡..."`)은 크롤링 파싱 오류로, 주소 파서가
  아니라 크롤러 쪽 별도 조치가 필요한 문제.

### 교훈
- 버그를 하나씩 발견할 때마다 그 케이스만 고치는 대신, 전체 운영
  데이터로 같은 클래스의 버그가 더 있는지 한 번에 훑는 게 장기적으로
  더 효율적임 — 이번에도 追記 4, 8에서 물건 하나씩 재현하며 고치던
  패턴을 사용자가 먼저 "전수 점검하자"고 제안해 한 번에 61건을
  정리했음.
- 정규식으로 "한글 1글자+동"을 뽑을 때는 반드시 실제 값 분포를
  확인해야 한다 — 한국 주소는 법정동명 자체가 거의 항상 "~동"으로
  끝나기 때문에, 건물동 표기와 법정동명이 정규식 레벨에서 구분이 안
  됨. 화이트리스트(실제 쓰이는 값만 허용)가 안전한 해법.

## 2026-07-23 追記 10: ROAD 타입 조회가 지번 숫자를 도로명으로 오인해
엉뚱한 좌표를 반환하는 버그 — 追記 9의 검증 범위 밖이었던 이유

### 문제
"2025타경101170"(경기 안양시 만안구 안양동 16-2, 디아망 1102호) 물건의
부가세 자동계산이 "이 호실(1102)의 전유부 정보를 건축물대장에서 찾지
못했습니다"로 실패. 사용자가 "아까 다 검증했던거 아니야?? 분명 조회
안되는거 없다고 했잖아 — 검증에 무슨 문제가 있는거야?"라고 정확히
지적.

### 追記 9 검증이 이 버그를 못 잡은 이유
追記 9의 전수 점검은 `parseAuctionAddress()`(주소 문자열 → {searchAddress,
dong, ho}) 함수만 로컬에서 시뮬레이션했다 — 외부 API를 전혀 호출하지
않는 순수 문자열 파싱 검증이었음. 이번 버그는 그 다음 단계, 즉
"잘라낸 searchAddress를 VWorld에 실제로 던졌을 때 정확한 좌표가
나오는가"에서 발생했다 — 파싱 결과 자체는 정확했지만(`searchAddress:
"경기도 안양시 만안구 안양동 16-2"`, `ho: "1102"`), 이 문자열을 VWorld
ROAD 타입으로 조회하는 단계에서 문제가 생겼다. 로컬 정규식 시뮬레이션
으로는 원천적으로 발견할 수 없는 종류의 버그였음.

### 원인
`address-to-coord` 라우트가 모든 주소를 항상 ROAD(도로명) 타입으로
먼저 조회했는데, "경기도 안양시 만안구 안양동 16-2"처럼 지번으로
끝나는 주소를 ROAD로 조회하면 VWorld가 "16-2"라는 숫자를 도로명의
건물번호로 잘못 해석해 **`status: OK`와 함께 완전히 다른 위치**를
반환했다(실측: "안양동 16-2" → ROAD 조회 시 "냉천로172번길 16-2"로
오인식 → 최종 PNU가 "안양동 627-236"이 되어버림, 실제로는 "안양동
16-2"여야 함). `status: OK`라서 이후 로직은 이 틀린 좌표를 정상
결과로 신뢰했고, 잘못된 PNU로 전유부를 조회하니 실제로 존재하는
1102호(전유 73.43㎡+공용 38.53㎡, 직접 curl로 확인)를 "찾지 못함"으로
처리했다.

### 수정
주소 끝부분이 지번 형태("동/읍/면 등 뒤에 숫자")인지 도로명 형태
("로/길로 끝나는 단어 뒤에 숫자")인지 정규식으로 구분해, 지번이면
PARCEL을 먼저 시도하도록 순서를 조건부로 변경(도로명이면 기존대로
ROAD 우선 유지). 두 형태 모두 "숫자" 또는 "숫자-숫자"로 끝나 그
패턴만으로는 구분이 안 되므로, 숫자 바로 앞 단어가 "로"/"길"로
끝나는지를 판별 기준으로 삼음.

### 검증
- 정규식 판별 로직을 전체 3872건에 시뮬레이션 — 지번 1594건, 도로명
  548건으로 분류(나머지는 두 패턴 다 해당 없음).
- 실측: "안양동 16-2"를 PARCEL로 조회하면 정확한 좌표(`detail:
  "디아망"`)와 PNU("안양동 16-2")가 나오고, 이 PNU로 전유부를
  페이지네이션 조회하면 1102호가 정상적으로 존재함을 확인.
- 타입체크 통과, 커밋 `53be441` 배포 완료.

### 교훈 (사용자 지적 반영)
- "전수 점검했다"는 말은 검증 범위를 명확히 해야 한다 — 이번처럼
  로컬 로직(파싱)만 검증하고 외부 API 호출 단계는 검증하지 않았다면,
  "조회 안 되는 게 없다"가 아니라 "파싱 단계에서는 문제가 없다"로
  범위를 좁혀 말했어야 함. 사용자가 "검증에 문제 있냐"고 재확인한
  덕에 검증 범위의 착시를 바로잡을 수 있었음.
- 외부 지오코딩 API가 "성공(status:OK)"을 반환해도 결과가 항상
  올바르다는 보장은 없다 — 애매한 입력(숫자로 끝나는 주소)에 대해
  다른 해석으로 매칭해버릴 수 있으므로, 여러 타입(ROAD/PARCEL)의
  결과를 교차 검증하거나 최소한 입력 형태에 맞는 타입을 먼저 시도하는
  것이 안전함.

### 교훈
- 서드파티 API(공공데이터포털 건축물대장)가 하나의 필드로 여러 법적
  분류를 뭉뚱그려 제공할 수 있다는 걸 놓치기 쉬움 — 참조 사이트와
  값이 다를 때 "지수표 자체가 틀렸나"만 의심하지 말고, 애초에 입력값
  (용도 분류) 단계에서 정보가 부족해 잘못 매칭됐을 가능성도 함께
  점검해야 함.

## 2026-07-24 追記 11: 부가세 자동계산 결과(PNU·구조·용도·층수) DB 캐싱

### 배경
